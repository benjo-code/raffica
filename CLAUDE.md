# Raffica

Raffica is a fast, open-source office suite for Windows, Linux and macOS, growing out of the PDF editor Pagewing: Raffica Office with Raffica Write, Sheets, Slides and PDF. Speed (startup, opening, scrolling) is the core promise; the suite should be as compatible as possible with DOCX/XLSX/PPTX. The suite is built step by step, starting with the PDF app (today's Pagewing core).

- **Stack:** .NET 10 (LTS) with Native AOT · Avalonia 12 for the shell · PDFium; the layout engine of Write is decided in the Write spec (see [Docs/DECISIONS.md](Docs/DECISIONS.md))
- **License:** GPL-3.0-or-later (as in Pagewing, see `LICENSE`)
- **Language:** everything in English: docs, README, commits, issues, PRs, code and comments · UI source language English, German localization from the first release
- **Build:** `dotnet build Raffica.slnx -c Release` · **Test:** once `dotnet run tools/native-fetch.cs -- --rid <win-x64|linux-x64> --out artifacts/native/<rid>` (OCR library), then `dotnet test Raffica.slnx -c Release --no-build --max-parallel-test-modules 1` with the environment variable `RAFFICA_REQUIRE_OCR=1` (a missing OCR library then fails the tests instead of skipping them) · **Format/Lint:** `dotnet format Raffica.slnx --verify-no-changes`
- **Roadmap:** [Docs/ROADMAP.md](Docs/ROADMAP.md) (generated, source [Docs/roadmap.json](Docs/roadmap.json), see "Maintaining the roadmap")
- **Decisions:** [Docs/DECISIONS.md](Docs/DECISIONS.md)
- **Specs:** `Docs/superpowers/specs/` · **Plans:** `Docs/superpowers/plans/`

## Project-specific

### Origin and migration from Pagewing

- Pagewing (`benjo-code/Pagewing`) is the predecessor and stays untouched. Its code is imported into this repo in M0 without git history; Pagewing is the read-only reference. Never modify the Pagewing checkout.
- Import only what is strictly needed: core/engine code, tests, build config, CI, LICENSE, README (rewritten). Do not import old plans, old docs or Pagewing's `DECISIONS.md` wholesale; write a new, short `Docs/DECISIONS.md` with only the decisions that still apply. Docs that are carried over are translated to English.
- Export the import from the `v1.0.0` tag of Pagewing (tracked files only, e.g. `git archive`), never copy the working folder (it contains build output).
- Order of the import: commit 1 = unchanged import, commit 2 = scripted rename (namespaces, AssemblyName, CLI, MSBuild properties, pipe name, desktop file, updater URLs, Inno Setup AppId). Run the rename script as a dry run first and read the list of hits. The Inno Setup AppId needs a new GUID and the updater needs its own signing key and URLs.
- The import branch must be merged with "Create a merge commit" so the two commits survive.

### Identity

- Commit only with the GitHub noreply address (`git config user.email`). The setting "Block command line pushes that expose my email" is enabled on the account.

### Design

- The UI is designed from scratch, one shared design system (tokens, typography, spacing, components) with one accent color per app. Check the contrast of every accent in the light and dark theme (WCAG).
- Use the Impeccable skill (`/impeccable init` creates `PRODUCT.md` and `DESIGN.md`) for direction and critique. Impeccable targets web frontends, so its tokens are implemented by hand in the shared shell project (AXAML).

### macOS

- No paid Apple account: no notarization, no Developer ID. Ad-hoc signing only (required on Apple Silicon; sign again after assembling the `.app` bundle). The README documents the first launch ("Open Anyway" in System Settings → Privacy & Security).
- Spec: `Docs/superpowers/specs/2026-11-09-raffica-macos-design.md` (milestones 3.1 to 3.3); decisions "Raffica on macOS: scope and Mac conventions (M3)" and "... speed checks and CI (M3)" in `Docs/DECISIONS.md`.
- **M3.1 (runs on the Mac):** decision "Raffica on macOS: native libraries, paths and activation (M3.1)". Minimum macOS 15.0 is `MACOS_DEPLOYMENT_TARGET` in `packaging/native/versions.txt` (3.3 reads it for `LSMinimumSystemVersion`).
- **Paths:** `PathRules` (Core) decides how paths compare (Windows and Linux as before, macOS `Ordinal` or NFC + `OrdinalIgnoreCase`); never choose path case by an OS check at a call site (`NoSourceFileChoosesPathCaseByWindowsCheck`, single-line regex). `FileIdentity` uses `stat$INODE64` on x64 and `stat` on arm64; the real calls are proven by CI only.
- **Activation:** `FileActivationBridge` (queue until `Attach`) with `AvaloniaFileActivationSource` delivers Finder files; wired in `App` on macOS only, not in measurement runs; Reopen is `IReopenSource` of `WindowHost` (M3.2).
- **M3.2 (feels like a Mac app):** decision "Raffica on macOS: menu bar, keys and life cycle (M3.2)". Owner's checklist: `packaging/README.md`, "Manual check on a Mac (M3.2)".
- **Life cycle:** `WindowHost` (`src/Raffica.Pdf/Hosting`, with `IHostedWindow`) keeps the app alive without a window on macOS, makes the next window (Dock reopen, Finder file) and runs ⌘Q through the window's close questions; files a closing window never opened come back through `IHostedWindow.TakeUndelivered`; `WindowSettingsSource` makes a later window read the settings the earlier one wrote. `App.CreateWindow` is the one place that makes a window; the host is macOS-only and absent in measurement runs.
- **Menu bar:** `MacMenuModel` (the menu as data) and `MacMenuBinder` (builds the `NativeMenu`, state from the command, `NeedsUpdate` and `WindowHost.CurrentChanged`) in `src/Raffica.Pdf/Platform/MacOS`; a menu item that runs a command shows the catalog's label and shortcut, so a new command is a line in the model, not new behavior. Avalonia takes the `NativeMenu` of the **Application** as the application menu only; File, Edit, View, Window and Help come from the menu set on each **window** (`MacWindowMenu.Attach`, a `MenuPart.Window` binder per window from `App.CreateWindow`), the application menu is the `MenuPart.App` binder of `App.AttachMenu` (Open only while no window exists); `Application.Name` titles it. Never put the whole bar on the application (decision "Raffica PDF on macOS: the menus belong to the window ...").
- **Keys:** `CatalogCommand.ShortcutFor(bool macOs)` (`macShortcut`, today only `ocr.run`: ⇧⌘R) and `ReservedShortcuts` (the macOS reserved list and the audit, pinned by `ReservedShortcutTests`); `KeyTips.Offered(macOs)` is false on macOS (no key tips, no ⌥ capture); `OrganizeList.CommandModifier` is the page list's command key.
- **Printing:** `CupsPrintService` and `CupsNative` (`libcups.2.dylib`) stay in `src/Raffica.Pdf/Platform/Linux` and serve macOS through `PlatformPrintServices.Choose`.
- **CI:** `build-macos` (macos-15 arm64, x64 build under Rosetta) runs on a PR into `main`, a push to `main`, the label `ci:macos` or a path from `.github/scripts/macos-paths.sh`; adding any label re-runs the whole CI (`labeled` type); it uploads the Intel disk image `raffica-pdf-macos-x64-dmg` (3 days) for the owner's manual check (M3.3).
- **Mac check and bundle:** `dotnet run tools/package.cs -- macos-app` builds the ad-hoc signed `Raffica PDF.app` (bundle, `Info.plist` from `MACOS_DEPLOYMENT_TARGET`, icon, signing; macOS only); steps in `packaging/README.md`, "Manual check on a Mac (M3.1)".
- **Native libraries:** `tools/check-binary.cs` also checks Mach-O files (`MachORules`: only `/usr/lib`, `/System/Library` or files inside the bundle; `selftest`). The macOS Tesseract is built by `packaging/native/build-macos.sh` through `native-tesseract.yml` with `-f build=2 -f systems=macos` (release `native-tesseract-5.5.4-2`); `tools/native-fetch.cs` pins both `.dylib` files. Lessons: macOS bash 3.2 needs `eval "$(...)"` instead of `source <(...)`; the x86_64 build needs `target-processor.cmake` as `CMAKE_PROJECT_INCLUDE` because Tesseract takes the processor from the host; a rerun needs a new release number and a failed run leaves an empty prerelease to delete first.
- **M3.3 (package and release):** decision "Raffica on macOS: packaging, default app and updates (M3.3)". Owner's checklist: `packaging/README.md`, "Manual check on a Mac (M3.3)". **Bundle and image:** `tools/package.cs` `macos-app` (class `MacApp`: `Info.plist`, `RafficaPdf.icns` through `sips` and `iconutil`, signing in the order every Mach-O, then the bundle, then `codesign --verify --deep --strict`), `dmg` and `dmg-smoke` (`Dmg`, `DmgSmoke`: the 5-second start under `arch -x86_64` for the Intel image); the dylibs stay in `Contents/MacOS` but tessdata is in `Contents/Resources/tessdata` (codesign takes a folder in `Contents/MacOS` for code and the first `build-macos` run failed on it; `macos-app` moves it there and refuses any other folder of a publish folder; `TessdataStore.ShippedDirectoryFor` has one bundle rule for `X.app/Contents/MacOS`); only stable `X.Y.Z` versions (a prerelease tag fails `release-macos` on purpose); files `RafficaPdf-<v>-macos-arm64.dmg`, `...-macos-x64.dmg`, `SHA256SUMS-macos.txt`; the manifest kinds `UpdateFileKinds.MacOsArm64Dmg` and `MacOsX64Dmg` are optional as a pair (the third sums file of `update-manifest`; the four-kind manifest and the signed vector stay byte-identical). **Update:** `PackageForm.MacAppArm64` and `MacAppX64` follow the process architecture (an Intel build under Rosetta takes the Intel image); `MacBundle` (path and location: installed, translocated, mounted image), `MacAppUpdater` with `MacAppUpdaterSetup` (attach at an explicit mount point, `ditto`, always detach, check, then `MacSwapScript`) and `MacSwapScript` (a detached `/bin/sh` that waits for the process, re-checks the staged bundle with `codesign`, swaps with a backup and reopens; every path is a positional argument, never script text). This is a deliberate deviation from `--finish-update`, which stays Windows-only. A failed start of the script is `InstallFailed`, not `NotStarted` (that wording says the new version is installed); a mounted image or a translocated copy is refused at apply time (`UpdateApplyProblem.RunsFromDownload`, the image is downloaded first). **Default app:** `MacDefaultAppService` over `ILaunchServices` and `LaunchServicesNative` (C API `LSSetDefaultRoleHandlerForContentType`, deprecated; no Objective-C runtime), supported only from an installed bundle; the handler id comes back in lower case, so it is compared ignoring case. **CI and release:** `build-macos` steps "Self-test of the packaging tool", "Bundle, image and smoke (both architectures)" (also `licenses.cs check` and `smoke-cli.cs` on the bundle's CLI) and "Sizes of the published app" (`size --check <rid>` against the `macos` budget entry, both architectures, fails the job above a limit; the `macos` entry of `s_pdfBudgets` holds the four size limits (size, zip, app, dmg; CI run 42865447655) and, since the owner's Intel measurement of 2026-11-11 (`measure.yml` platform `macos`, run 43089378750, CSVs in `Docs/measurements/pdf-viewer-2026-11-11-macos/`), the six time and memory limits (cold 780, warm 720, thousand 740, second 60, scroll 30 ms, memory 115 MiB as budgets; ### Write library (M4.1)

- **Where:** `src/Raffica.Write.Model` (the UI-free document model: `WordDocument`, `Story`, blocks and inlines, `PropertyBag`, `UnknownContent`, `SchemaOrder`; references nothing), `src/Raffica.Write.Docx` (`DocxFile`, the part codecs, `Xml/PartXml`; references only Model, Core and the Open XML SDK), `tests/Raffica.Write.Tests`, `bench/write-corpus` (the corpus tool, `AssemblyName` `write-corpus`), `testdata/write-corpus` (manifest, files, licence texts, `README.md`) and `Docs/write-corpus.md` (generated). `ProjectGuardTests` pins the references. Decision "Raffica Write: document model and DOCX package layer (M4.1)" in `Docs/DECISIONS.md`.
- **Vocabulary rule:** the model is the vocabulary of the whole of Write; later milestones add accessors and views (like `FieldScanner` and `TrackedChanges`), never a second storage. Everything the model does not understand stays in place as `UnknownContent` (the `Unknown*` types hold one by composition); new children are placed by `SchemaOrder`, so a code-made child is schema-valid. Position ints on tables, rows and cells and the order of read list items are not edit-proof: an editor must account for them. A comment with `Done` or a parent needs a paragraph `w14:paraId` (`CommentCollection.EnsureParaId`, `Write` throws without).
- **Save rule:** `DocxFile.Open(path, DocxParts)` reads through the SDK's package layer only (never its typed DOM); `DocxFile.SaveAsync` rewrites every loaded model part (equal content, not equal bytes), keeps every other part byte-identical and checks that (and the relationship and content-type structure) in a guard before the replace; a refused save is `DocxSaveException` (`PartsChanged`, `ModelNotReadable`), an unreadable file `DocxFormatException`. A save over the opened file (links resolved) is refused with `SaveFailureException` (`OriginalChanged`) before anything is written when its `FileStamp` (taken before the read, as for a PDF) differs or the file is gone, unless the caller passes `overwriteChangedOriginal` (the overload `SaveAsync(path, bool, token)`; the analyzer wants the token last); a successful save over the opened file records the new stamp, a save to another path changes neither the stamp nor the snapshot, and `Open(bytes)` has no origin and no check. Tests break the steps through the internal seams `BeforeReplace`, `WrapPartWrite` and `AfterPackageWritten`. The model must not change while a save runs. Hostile-file hardening is 4.8.
- **`AtomicFile` (Core, `Saving`):** the atomic replace shared by `DocumentSaver` and `DocxFile` (`ResolveLink`, `NewTemporaryPath`, `MoveIntoPlace`, `TargetMetadata`, `FlushToDisk`); change it with the PDF save tests in mind (`*Saving*` in Core, `SaveControllerTests` in Pdf).
- **Corpus:** every file is in `testdata/write-corpus/corpus.json` (id, SHA-256, source, SPDX licence from the allowed list, licence file, retrieval date, feature tags found by `FeatureDetector`); a file whose content licence is unclear is left out (five POI files were removed for that). Commands: `dotnet run --project bench/write-corpus -c Release -- check|run|add|pdf-facts|compare|table ...` (all take `--root`; exit 0 ok, 1 findings, 2 bad input). To add a file, use `add` (steps in `testdata/write-corpus/README.md`), then `check`, `run` and `CorpusRoundTripTests`, and commit file, licence and manifest together. `Docs/write-corpus.md` comes from `table` and is not checked by CI or a test: regenerate it by hand and commit it whenever the corpus or the round trip changes. The Word PDFs are the owner's (`word.pdf`, `word-accept.pdf`, `word-reject.pdf` next to the entry); the comparison tool has the Word side only until 4.2.
- **Pitfalls:** the compiler drops unused assembly references, so a reference guard only sees references the code really uses. The Native AOT publish of the tool on Windows needs the `Microsoft Visual Studio\Installer` folder on `PATH`, and CI searches its log for `IL[23][0-9]{3}`. The SDK throws on a relationship to a missing part, so `DocxFile.Open` refuses such a file. Test scripts that write CRLF fail `dotnet format`. The Unix-mode save test skips on Windows and only CI on Linux and macOS runs it. Tests of the Write project run with `dotnet test tests/Raffica.Write.Tests -c Release --filter-class "*Name"`; a filter that matches nothing selects nothing silently, so check the count. A file's text is never printed by the tool or put into an exception message.

### Shell

- **Where:** `src/Raffica.Shell/Styles` holds `Tokens.axaml` (light and dark), `Tokens.HighContrast.axaml`, `Metrics.axaml`, `Typography.axaml`, `Fonts.axaml`, `Icons.axaml`, `Focus.axaml` and `Controls/*` (one file per control). `src/Raffica.Gallery` is the gallery app, `tests/Raffica.Shell.Tests` the shell tests.
- **Keys:** colours are `Raffica.Color.<Group>.<Name>`, brushes `Raffica.Brush.*`. Component styles use these semantic tokens only; hex literals in component styles fail `NoHexInComponentStylesTests`. A new colour token must be classified in the contrast policy (`EveryTokenIsClassified` fails otherwise) and added to `TokenValuesTests`, `Tokens.axaml` (Light and Dark), `Tokens.HighContrast.axaml` and the token list of the gallery's `FoundationsSection`.
- **Theme:** `ShellTheme.Apply` sets theme mode, app ink and high contrast. Fluent stays underneath for controls that are not restyled.
- **Strings:** English and German live in `Strings.en.resx` and `Strings.de.resx`, both embedded in the assembly; a missing key throws. `TranslationTests` finds every `Strings.en.resx` under `src/` and requires a German value for each key, so every new string needs both files.
- **Gallery switches:** `--lang en|de`, `--theme`, `--high-contrast`, `--ink`, `--section`, `--screenshot`, `--open-menu`, `--open-dialog`, `--view gallery|frame` (default `gallery`), `--compact` (frame view: compact command bar), `--settings-file <path>` (frame view: settings file instead of the default), `--measure-startup`, `--measure-input`, `--measure-memory` (frame view only) and `--print-string <key>` (prints one string and exits, used by the CI smoke test). `RafficaGallery.exe` is a GUI-subsystem exe, so the `--print-string` output is only visible when redirected (the CI step uses `Start-Process -RedirectStandardOutput`). The gallery tests run headless and need no display; screenshots need a real display.
- **Frame:** the shared app frame lives in `src/Raffica.Shell/Frame` with its styles in `Styles/Frame/*.axaml`; the gallery shows it as `FrameDemoWindow` (`--view frame`). `dotnet run bench/shell-probe/measure.cs -- check ...` compares a `measure.yml` gallery run with the limits of `Docs/DECISIONS.md` ("Gallery frame baseline (M1.2)") and `... -- size --check <rid> --publish-dir <dir> --fonts-dir src/Raffica.Shell/Assets/Fonts` checks the published size (CI step "Size of the published gallery").
- **Ribbon (M2.7):** `RibbonView` decides the layout (`IsCompact` is the user's setting, `IsEffectivelyCompact` adds "the window is narrower than the full band of the active tab"; chevrons scroll a band that is still too wide). A command that is a switch or choice gets `CommandDefinition.CheckedWhen` (read again by `RefreshCommandStates`): class `checked` (ink fill) and the UIA Toggle pattern; the PDF catalog marks them with `toggle: true` and `PdfWindow.IsCommandOn` reads the state, `UpdateCheckedStates` asks the ribbon again only when it changed. A tile label breaks only at spaces and hyphens (`RibbonButton.RibbonLabel`); key tips cover no text (`BadgePlacement`, checked by `BadgeFit`); the long wording of a command is its `Description` (`Desc<Name>` strings). `Docs/DECISIONS.md`, "Raffica shell: ribbon overflow (M2.7)" and "Raffica shell: ribbon labels, on state and key tips (M2.7)".

### PDF app

- **Where:** `src/Raffica.Pdf` (`AssemblyName` `RafficaPdf`, root namespace `Raffica.Pdf`), tests in `tests/Raffica.Pdf.Tests`. It depends on `Raffica.Core` and `Raffica.Shell` only. The frame is the shell's; the app builds the ribbon (`PdfRibbon`), the command catalog (`Commands/PdfCommandCatalog`), panes, page view (`Viewing/PageView`) and dialogs.
- **Files:** two settings files without a merge: the shell's `ShellSettings` (`Raffica/Pdf/settings.json`: theme, language, compact bar) and Core's `AppSettings` (`pdf-settings.json`: page appearance, default layout and zoom mode, print scaling, last printer), plus Core's `recent.json` (recent files and the position per file) and the `signatures` folder of the saved signatures (`PdfSettingsFiles.SignaturesDirectoryFor`; the user's data folder by default). `--settings-file <path>` redirects all of them (the other files and the folder live next to the given file) and the single-instance pipe name (hash suffix); tests and measurements always pass it.
- **Switches:** `--lang en|de`, `--theme`, `--high-contrast`, `--settings-file <path>`, `--print-string <key>` (prints one string and exits, used by the CI smoke test) and the measurement switches `--measure-startup`, `--measure-second`, `--measure-scroll`, `--measure-memory` (one per run, each needs `--settings-file` and a file).
- **Rendering:** on Windows the PDF app renders in software (`Win32RenderingMode.Software` as the only mode) by default, because that halves every start case and cuts idle memory to a third (`Docs/DECISIONS.md`, "Raffica PDF: software rendering is the Windows default (M2.1 follow-up)"). The environment variable `RAFFICA_RENDERING` (read in `Program.BuildAvaloniaApp`, parsed by `RenderingChoiceParser`) is the opt-out: `default` (any case) selects Avalonia's own path (ANGLE/GPU) for comparison or a user with a problem; `software`, empty, unset or anything else gives software. Linux is untouched; on macOS `software` also selects Avalonia's software rendering (opt-in only: the Intel measurement of 2026-11-11 found it worse on memory, the second file and scrolling, so the macOS default stays Avalonia's own path, `Docs/DECISIONS.md`, "Raffica on macOS: the Intel budgets and the rendering default (M3.3)"); there is no setting and no UI. `measure.yml` passes it with its input `rendering` (`app`, `software`, `default`).
- **Measuring:** `dotnet run bench/shell-probe/measure.cs -- ... --target pdf` (method in `Docs/DECISIONS.md`, "Raffica PDF measurement method (M2.1)"). The limit table `s_pdfBudgets` in `CheckCommand` holds the M2.1 budgets with the M2.5 size amendment (`Docs/DECISIONS.md`, "Raffica PDF speed budgets (M2.1)" and "... published size budgets after the OCR payload (M2.5)"); `check --target pdf` compares a run with them.
- **Platform code:** ported platform code (printing, later default-app registration) lives in `src/Raffica.Pdf/Platform/<OS>`, never in UI code; the UI reaches it through `PlatformPrintServices.Create`. Real printers, CUPS and the Win32 dialog need the owner's machines (`CupsPrintServiceTests` skip without `RAFFICA_TEST_CUPS_PRINTER`).
- **Tests:** the Pdf tests run headless. Run one class with `dotnet test tests/Raffica.Pdf.Tests -c Release --filter-class "*MeasurementTests"`; `--filter-namespace "*Platform*"` selects the print tests. A filter that matches nothing selects nothing silently, so check the count.
- **Pool-thread callbacks:** a handler of a scheduler, session, timer or progress event that can run on a pool thread must never read `Dispatcher.UIThread` at post time or on a pool thread (headless tests clear it between tests and a pool thread would recreate it, `TeardownRaceTests`); the owner captures the dispatcher on the UI thread when it is constructed (`Dispatcher` of a control, a `_dispatcher` field of other owners, the sessions' `SynchronizationContext`) and posts and checks access through it.
- **Dialogs and keys:** cards (open errors, password, link, go to page, document info, help, print) go through `DialogQueue`; one-shot shortcuts ignore key repeat (`PdfShortcut.AllowsRepeat`). Every card footer is built by the shell's `CardFooter.Build(primary, secondary, cancel)` (primary first, Cancel last, `IsDefault` on the primary and `IsCancel` on the cancel; `CardFooter.Only` for one button) and every danger-colored hint by `ValidationHint.Mark` (an assertive live region); a new card factory must be listed in `CardFooterTests.Entries` (a reflection guard fails otherwise). Every command that the rules disable with a document open needs a reason in `PdfCommandRules.ReasonFor` (`PdfCommandRulesTests` walks every id in every state); a new key without a command goes into `NavigationHelp`.

## Maintaining the roadmap

The source of truth is `Docs/roadmap.json` (schema: `Docs/roadmap.schema.json`). `Docs/ROADMAP.md` is generated from it and never edited by hand. The .NET 10 SDK is required, even if the project otherwise uses a different stack.

1. Edit only `Docs/roadmap.json`: status, plan link, tick tasks and criteria (`"done": true`, proof in `"evidence"`), scope changes, backlog. Leave optional fields out, never set them to `null`.
2. Then run `dotnet run tools/roadmap.cs -- generate` and commit both files. Errors name the path in the JSON (for example `subprojects[0].milestones[2].completedOn`).
3. `dotnet run tools/roadmap.cs -- check` validates the schema and references and checks that `ROADMAP.md` is up to date; the CI (job `roadmap`) does the same.
4. Rules: `status` is `open`, `planned`, `in-progress` or `done`; `done` requires `completedOn` (YYYY-MM-DD), from `planned` on `plan` is required (path relative to `Docs/`); milestone ids are unique strings (`"5.1"` is allowed); prerequisites and `afterMilestone` must exist; title, goal and name are a single line; texts are Markdown; whatever fits nowhere goes into `blocks` (`title`, `text`).
5. A new milestone is an entry in `subprojects[].milestones`:

```json
{
  "id": "1", "title": "<title>", "status": "open",
  "prerequisites": ["0"],
  "goal": "<One sentence: what is possible after this milestone?>",
  "tasks": [ { "text": "…", "done": false } ],
  "acceptance": [ { "text": "… (verifiable: test, command or a concrete manual check)", "done": false } ]
}
```

   A new subproject is an entry in `subprojects` (`number`, `name`, `spec` with `text` and/or `link`, `milestones`), a release is an entry in `releases` (`version`, `title`, `status`, `afterMilestone`, optional `covers`, `date`, `intro`, `acceptance`, `blocks`).
6. Ideas belong in `backlog` (`title`, `text`, optional `idea`). The skill `/ideen` (from `benjo-code/Labjo`) enters adopted ideas there and regenerates `Docs/ROADMAP.md`.

## Milestone workflow

Every change "in the roadmap" (link a plan, set a status, tick tasks, scope changes) is a change to `Docs/roadmap.json` together with the regenerated `Docs/ROADMAP.md`, see "Maintaining the roadmap".

**"Plan milestone N":**
1. Create the branch `feature/mNN-<topic>` from the current `dev`. Plan, roadmap maintenance and implementation of the milestone all go through this branch.
2. Read `Docs/ROADMAP.md`, the spec of the subproject and the current state of the code.
3. Review the project's open ideas with `/ideen` (skill from `benjo-code/Labjo`, installation: `bash tools/install-ideen-skill.sh` there): adopt, implement or discard. Whatever belongs in the milestone flows into the plan. The roadmap change lives on the milestone branch (when asked, choose "current branch").
4. If the milestone starts with "Create spec" or the subproject has no spec yet: first work out the spec with the user by brainstorming and put it under `Docs/superpowers/specs/`.
5. Write the plan to `Docs/superpowers/plans/YYYY-MM-DD-milestone-NN-<topic>.md`. The plan covers exactly the tasks and acceptance criteria of the milestone, nothing more.
6. In the roadmap, link the plan and set the status to `🟡 planned` (overview table and milestone).

**Implementation:**
- Status `🔵 in progress`. Tick every finished task in the roadmap right away.
- Tick acceptance criteria only once they have actually been checked, and note the proof behind them (test name, command + result or manual check).
- At the end, status `✅ done` with the date in the table and the milestone, then a PR to `dev` (see "Git & branches").
- Record scope changes in the roadmap under "Scope changes", not silently in the code.
- Work only within the scope of the active milestone. Do not anticipate features, packages or architecture decisions of later milestones.

## Git & branches

- `main` contains only published states (releases). `dev` is the integration branch.
- Always work on `feature/<topic>` or `fix/<topic>`, branched from the current `dev` (`git switch dev && git pull && git switch -c feature/<topic>`).
- Before any work, check `git status` and the current branch. If on `main` or `dev`, create a feature branch first. Never commit directly to `main` or `dev`.
- Feature and fix branches go to `dev` via PR. Claude merges these PRs itself once the work is finished and all CI checks are green (squash merge allowed).
- PRs to `main` exist only for releases and hotfixes and only on the explicit instruction of the user.
- PRs between `main` and `dev` (release, hotfix, returning `main` → `dev`) are always merged with **"Create a merge commit"**, never by squash or rebase. Otherwise `main` and `dev` lose their common history and every release causes conflicts.
- Hotfix: branch `hotfix/<topic>` from `main` → PR to `main` → release (see below) → then merge `main` into `dev` via PR.
- Stage selectively (`git add <file>`). No `git add .` or `git add -A` if foreign changes that do not belong to the task are in the working tree. For files that were already modified before, read `git diff <file>` first and use `git add -p` if needed.
- After every commit, check `git show --stat HEAD` against the expected file list.
- Commit messages follow Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`, `ci:`, optionally with a scope (`feat(api): …`).
- Forbidden without explicit instruction: force push, `git reset --hard`, deleting branches, rewriting history, bypassing hooks with `--no-verify`.
- Always create new repos (including companion ones like `-Releases` or `-Privacy`) in the org `benjo-code`, always with the owner spelled out (`gh repo create benjo-code/<name> …`), never under the personal account. Then check with `gh repo view benjo-code/<name>`.

## Releases

- Versioning follows SemVer (`vMAJOR.MINOR.PATCH`).
- `CHANGELOG.md` → `[Unreleased]` is extended in every PR with a change worth mentioning for users (not for pure planning, roadmap or internal cleanup PRs).
- Procedure (only on instruction):
  1. Branch `release/vX.Y.Z` from `dev`, turn `[Unreleased]` in `CHANGELOG.md` into `[X.Y.Z] – YYYY-MM-DD` (name the included milestones) and add a new, empty `[Unreleased]` above it.
  2. PR `release/vX.Y.Z` → `main` (merge commit).
  3. Tag and GitHub release in one step: `gh release create vX.Y.Z --target main --title "vX.Y.Z" --notes "<CHANGELOG section>"`.
  4. Return `main` to `dev` via PR (merge commit) so the two do not drift apart.

## Project memory

- Document anything important for the future in the repo without being asked:
  - Architecture and technology decisions, fixed versions, rejected approaches → `Docs/DECISIONS.md`
  - Scope changes → `Docs/ROADMAP.md`, section "Scope changes"
  - Lasting project knowledge (architecture, conventions, workarounds, pitfalls) → this file, section "Project-specific"
- Do not record guesses, intermediate states or temporary diagnoses as facts.
- References name the file and the type, member or section, never line numbers (they go stale).

## Quality & proof

- "Done" means: build, test and format/lint (commands above) are demonstrably green. Name the command and the result.
- `dotnet run tools/roadmap.cs -- check` is part of "done": the roadmap is valid and `Docs/ROADMAP.md` is up to date.
- Whatever could not be verified (for example because real hardware or credentials are missing) is explicitly marked as open, together with the command that checks it.
- Do not suppress warnings, skip tests or weaken checks just to make something green.

## Security

- No secrets (tokens, passwords, keys, real credentials) in files, commits, logs, PRs or replies.
- Never quote or print values from `.env` or similar, only variable names or placeholders.
- Secrets come from env vars or a secret store. Keep a placeholder in `.env.example` for every required variable. `.env` is in `.gitignore`.

## Collaboration

- Ask when requirements are unclear instead of guessing.
- Destructive actions or actions with external effect (merge to `main`, release, deleting branches, tags, releases or repos, changes to GitHub settings) only on explicit instruction. Feature branches that are deleted automatically after the merge are excluded.
