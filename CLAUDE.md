# Raffica

Raffica is a fast, open-source office suite for Windows, Linux and macOS, growing out of the PDF editor Pagewing: Raffica Office with Raffica Write, Sheets, Slides and PDF. Speed (startup, opening, scrolling) is the core promise; the suite should be as compatible as possible with DOCX/XLSX/PPTX. The suite is built step by step, starting with the PDF app (today's Pagewing core).

- **Stack:** .NET 10 (LTS) with Native AOT · Avalonia 12 for the shell · PDFium; the layout engine of Write is decided in the Write spec (see [Docs/DECISIONS.md](Docs/DECISIONS.md))
- **License:** GPL-3.0-or-later (as in Pagewing, see `LICENSE`)
- **Language:** everything in English: docs, README, commits, issues, PRs, code and comments · UI source language English, German localization from the first release
- **Build:** `dotnet build Raffica.slnx -c Release` · **Test:** once `dotnet run tools/native-fetch.cs -- --rid <win-x64|linux-x64> --out artifacts/native/<rid>` (OCR library), then `dotnet test Raffica.slnx -c Release --no-build --max-parallel-test-modules 1` with the environment variable `RAFFICA_REQUIRE_OCR=1` (a missing OCR library then fails the tests instead of skipping them) · **Format/Lint:** `dotnet format Raffica.slnx --verify-no-changes`
- **Roadmap:** [Docs/ROADMAP.md](Docs/ROADMAP.md) (generated, source [Docs/roadmap.json](Docs/roadmap.json), see "Maintaining the roadmap")
- **Decisions:** [Docs/DECISIONS.md](Docs/DECISIONS.md)
- **Specs:** `Docs/superpowers/specs/` · **Plans:** `Docs/superpowers/plans/`

## Project-specific

### Origin and migration from Pagewing

- Pagewing (`benjo-code/Pagewing`) is the predecessor and stays untouched. Its code is imported into this repo in M0 without git history; Pagewing is the read-only reference. Never modify the Pagewing checkout.
- Import only what is strictly needed: core/engine code, tests, build config, CI, LICENSE, README (rewritten). Do not import old plans, old docs or Pagewing's `DECISIONS.md` wholesale; write a new, short `Docs/DECISIONS.md` with only the decisions that still apply. Docs that are carried over are translated to English.
- Export the import from the `v1.0.0` tag of Pagewing (tracked files only, e.g. `git archive`), never copy the working folder (it contains build output).
- Order of the import: commit 1 = unchanged import, commit 2 = scripted rename (namespaces, AssemblyName, CLI, MSBuild properties, pipe name, desktop file, updater URLs, Inno Setup AppId). Run the rename script as a dry run first and read the list of hits. The Inno Setup AppId needs a new GUID and the updater needs its own signing key and URLs.
- The import branch must be merged with "Create a merge commit" so the two commits survive.

### Identity

- Commit only with the GitHub noreply address (`git config user.email`). The setting "Block command line pushes that expose my email" is enabled on the account.

### Design

- The UI is designed from scratch, one shared design system (tokens, typography, spacing, components) with one accent color per app. Check the contrast of every accent in the light and dark theme (WCAG).
- Use the Impeccable skill (`/impeccable init` creates `PRODUCT.md` and `DESIGN.md`) for direction and critique. Impeccable targets web frontends, so its tokens are implemented by hand in the shared shell project (AXAML).

### macOS

- No paid Apple account: no notarization, no Developer ID. Ad-hoc signing only (required on Apple Silicon; sign again after assembling the `.app` bundle). The README documents the first launch ("Open Anyway" in System Settings → Privacy & Security).
- Spec: `Docs/superpowers/specs/2026-11-09-raffica-macos-design.md` (milestones 3.1 to 3.3); decisions "Raffica on macOS: scope and Mac conventions (M3)" and "... speed checks and CI (M3)" in `Docs/DECISIONS.md`.
- **M3.1 (runs on the Mac):** decision "Raffica on macOS: native libraries, paths and activation (M3.1)". Minimum macOS 15.0 is `MACOS_DEPLOYMENT_TARGET` in `packaging/native/versions.txt` (3.3 reads it for `LSMinimumSystemVersion`).
- **Paths:** `PathRules` (Core) decides how paths compare (Windows and Linux as before, macOS `Ordinal` or NFC + `OrdinalIgnoreCase`); never choose path case by an OS check at a call site (`NoSourceFileChoosesPathCaseByWindowsCheck`, single-line regex). `FileIdentity` uses `stat$INODE64` on x64 and `stat` on arm64; the real calls are proven by CI only.
- **Activation:** `FileActivationBridge` (queue until `Attach`) with `AvaloniaFileActivationSource` delivers Finder files; wired in `App` on macOS only, not in measurement runs; Reopen is `IReopenSource` of `WindowHost` (M3.2).
- **M3.2 (feels like a Mac app):** decision "Raffica on macOS: menu bar, keys and life cycle (M3.2)". Owner's checklist: `packaging/README.md`, "Manual check on a Mac (M3.2)".
- **Life cycle:** `WindowHost` (`src/Raffica.Pdf/Hosting`, with `IHostedWindow`) keeps the app alive without a window on macOS, makes the next window (Dock reopen, Finder file) and runs ⌘Q through the window's close questions; files a closing window never opened come back through `IHostedWindow.TakeUndelivered`; `WindowSettingsSource` makes a later window read the settings the earlier one wrote. `App.CreateWindow` is the one place that makes a window; the host is macOS-only and absent in measurement runs.
- **Menu bar:** `MacMenuModel` (the menu as data) and `MacMenuBinder` (builds the `NativeMenu`, state from the command, `NeedsUpdate` and `WindowHost.CurrentChanged`) in `src/Raffica.Pdf/Platform/MacOS`; a menu item that runs a command shows the catalog's label and shortcut, so a new command is a line in the model, not new behavior. Avalonia takes the `NativeMenu` of the **Application** as the application menu only; File, Edit, View, Window and Help come from the menu set on each **window** (`MacWindowMenu.Attach`, a `MenuPart.Window` binder per window from `App.CreateWindow`), the application menu is the `MenuPart.App` binder of `App.AttachMenu` (Open only while no window exists); `Application.Name` titles it. Never put the whole bar on the application (decision "Raffica PDF on macOS: the menus belong to the window ...").
- **Keys:** `CatalogCommand.ShortcutFor(bool macOs)` (`macShortcut`, today only `ocr.run`: ⇧⌘R) and `ReservedShortcuts` (the macOS reserved list and the audit, pinned by `ReservedShortcutTests`); `KeyTips.Offered(macOs)` is false on macOS (no key tips, no ⌥ capture); `OrganizeList.CommandModifier` is the page list's command key.
- **Printing:** `CupsPrintService` and `CupsNative` (`libcups.2.dylib`) stay in `src/Raffica.Pdf/Platform/Linux` and serve macOS through `PlatformPrintServices.Choose`.
- **CI:** `build-macos` (macos-15 arm64, x64 build under Rosetta) runs on a PR into `main`, a push to `main`, the label `ci:macos` or a path from `.github/scripts/macos-paths.sh`; adding any label re-runs the whole CI (`labeled` type); it uploads the Intel disk image `raffica-pdf-macos-x64-dmg` (3 days) for the owner's manual check (M3.3).
- **Mac check and bundle:** `dotnet run tools/package.cs -- macos-app` builds the ad-hoc signed `Raffica PDF.app` (bundle, `Info.plist` from `MACOS_DEPLOYMENT_TARGET`, icon, signing; macOS only); steps in `packaging/README.md`, "Manual check on a Mac (M3.1)".
- **Native libraries:** `tools/check-binary.cs` also checks Mach-O files (`MachORules`: only `/usr/lib`, `/System/Library` or files inside the bundle; `selftest`). The macOS Tesseract is built by `packaging/native/build-macos.sh` through `native-tesseract.yml` with `-f build=2 -f systems=macos` (release `native-tesseract-5.5.4-2`); `tools/native-fetch.cs` pins both `.dylib` files. Lessons: macOS bash 3.2 needs `eval "$(...)"` instead of `source <(...)`; the x86_64 build needs `target-processor.cmake` as `CMAKE_PROJECT_INCLUDE` because Tesseract takes the processor from the host; a rerun needs a new release number and a failed run leaves an empty prerelease to delete first.
- **M3.3 (package and release):** decision "Raffica on macOS: packaging, default app and updates (M3.3)". Owner's checklist: `packaging/README.md`, "Manual check on a Mac (M3.3)". **Bundle and image:** `tools/package.cs` `macos-app` (class `MacApp`: `Info.plist`, `RafficaPdf.icns` through `sips` and `iconutil`, signing in the order every Mach-O, then the bundle, then `codesign --verify --deep --strict`), `dmg` and `dmg-smoke` (`Dmg`, `DmgSmoke`: the 5-second start under `arch -x86_64` for the Intel image); the dylibs stay in `Contents/MacOS` but tessdata is in `Contents/Resources/tessdata` (codesign takes a folder in `Contents/MacOS` for code and the first `build-macos` run failed on it; `macos-app` moves it there and refuses any other folder of a publish folder; `TessdataStore.ShippedDirectoryFor` has one bundle rule for `X.app/Contents/MacOS`); only stable `X.Y.Z` versions (a prerelease tag fails `release-macos` on purpose); files `RafficaPdf-<v>-macos-arm64.dmg`, `...-macos-x64.dmg`, `SHA256SUMS-macos.txt`; the manifest kinds `UpdateFileKinds.MacOsArm64Dmg` and `MacOsX64Dmg` are optional as a pair (the third sums file of `update-manifest`; the four-kind manifest and the signed vector stay byte-identical). **Update:** `PackageForm.MacAppArm64` and `MacAppX64` follow the process architecture (an Intel build under Rosetta takes the Intel image); `MacBundle` (path and location: installed, translocated, mounted image), `MacAppUpdater` with `MacAppUpdaterSetup` (attach at an explicit mount point, `ditto`, always detach, check, then `MacSwapScript`) and `MacSwapScript` (a detached `/bin/sh` that waits for the process, re-checks the staged bundle with `codesign`, swaps with a backup and reopens; every path is a positional argument, never script text). This is a deliberate deviation from `--finish-update`, which stays Windows-only. A failed start of the script is `InstallFailed`, not `NotStarted` (that wording says the new version is installed); a mounted image or a translocated copy is refused at apply time (`UpdateApplyProblem.RunsFromDownload`, the image is downloaded first). **Default app:** `MacDefaultAppService` over `ILaunchServices` and `LaunchServicesNative` (C API `LSSetDefaultRoleHandlerForContentType`, deprecated; ### Write library (M4.1)

- **Where:** `src/Raffica.Write.Model` (the UI-free document model: `WordDocument`, `Story`, blocks and inlines, `PropertyBag`, `UnknownContent`, `SchemaOrder`; references nothing), `src/Raffica.Write.Docx` (`DocxFile`, the part codecs, `Xml/PartXml`; references only Model, Core and the Open XML SDK), `tests/Raffica.Write.Tests`, `bench/write-corpus` (the corpus tool, `AssemblyName` `write-corpus`), `testdata/write-corpus` (manifest, files, licence texts, `README.md`) and `Docs/write-corpus.md` (generated). `ProjectGuardTests` pins the references. Decision "Raffica Write: document model and DOCX package layer (M4.1)" in `Docs/DECISIONS.md`.
- **Vocabulary rule:** the model is the vocabulary of the whole of Write; later milestones add accessors and views (like `FieldScanner` and `TrackedChanges`), never a second storage. Everything the model does not understand stays in place as `UnknownContent` (the `Unknown*` types hold one by composition); new children are placed by `SchemaOrder`, so a code-made child is schema-valid. Position ints on tables, rows and cells and the order of read list items are not edit-proof: an editor must account for them. A comment with `Done` or a parent needs a paragraph `w14:paraId` (`CommentCollection.EnsureParaId`, `Write` throws without).
- **Save rule:** `DocxFile.Open(path, DocxParts)` reads through the SDK's package layer only (never its typed DOM); `DocxFile.SaveAsync` rewrites every loaded model part (equal content, not equal bytes), keeps every other part byte-identical and checks that (and the relationship and content-type structure) in a guard before the replace; a refused save is `DocxSaveException` (`PartsChanged`, `ModelNotReadable`), an unreadable file `DocxFormatException`. A save over the opened file (links resolved) is refused with `SaveFailureException` (`OriginalChanged`) before anything is written when its `FileStamp` (taken before the read, as for a PDF) differs or the file is gone, unless the caller passes `overwriteChangedOriginal` (the overload `SaveAsync(path, bool, token)`; the analyzer wants the token last); a successful save over the opened file records the new stamp, a save to another path changes neither the stamp nor the snapshot, and `Open(bytes)` has no origin and no check. Tests break the steps through the internal seams `BeforeReplace`, `WrapPartWrite` and `AfterPackageWritten`. The model must not change while a save runs. Hostile-file hardening is 4.8.
- **`AtomicFile` (Core, `Saving`):** the atomic replace shared by `DocumentSaver` and `DocxFile` (`ResolveLink`, `NewTemporaryPath`, `MoveIntoPlace`, `TargetMetadata`, `FlushToDisk`); change it with the PDF save tests in mind (`*Saving*` in Core, `SaveControllerTests` in Pdf).
- **Corpus:** every file is in `testdata/write-corpus/corpus.json` (id, SHA-256, source, SPDX licence from the allowed list, licence file, retrieval date, feature tags found by `FeatureDetector`); a file whose content licence is unclear is left out (five POI files were removed for that). Commands: `dotnet run --project bench/write-corpus -c Release -- check|run|add|pdf-facts|compare|table ...` (all take `--root`; exit 0 ok, 1 findings, 2 bad input). To add a file, use `add` (steps in `testdata/write-corpus/README.md`), then `check`, `run` and `CorpusRoundTripTests`, and commit file, licence and manifest together. `Docs/write-corpus.md` comes from `table` and is not checked by CI or a test: regenerate it by hand and commit it whenever the corpus or the round trip changes. The Word PDFs are the owner's (`word.pdf`, `word-accept.pdf`, `word-reject.pdf` next to the entry); the comparison tool has Word's side (page count and text per page) and, since 4.2, Write's own layout side (see "Write viewer (M4.2)").
- **Pitfalls:** the compiler drops unused assembly references, so a reference guard only sees references the code really uses. The Native AOT publish of the tool on Windows needs the `Microsoft Visual Studio\Installer` folder on `PATH`, and CI searches its log for `IL[23][0-9]{3}`. The SDK throws on a relationship to a missing part, so `DocxFile.Open` refuses such a file. Test scripts that write CRLF fail `dotnet format`. The Unix-mode save test skips on Windows and only CI on Linux and macOS runs it. Tests of the Write project run with `dotnet test tests/Raffica.Write.Tests -c Release --filter-class "*Name"`; a filter that matches nothing selects nothing silently, so check the count. A file's text is never printed by the tool or put into an exception message. Known limits (list in the decision): `xml:space="default"` comes back as `preserve`, deep nesting overflows the stack until 4.8 adds a depth limit, Strict OOXML is refused, and `tools/licenses.cs` does not cover the Write projects (the SDK has no notice entry yet).

### Write viewer (M4.2)

- **Where:** `src/Raffica.Write.Layout` (the UI-free layout library, namespace `Raffica.Write.Layout`; references Model, SkiaSharp and HarfBuzzSharp and no Avalonia type; folders `Fonts`, `Text` (`LineBreaker`, `Hyphenator`), `Styles` (`StyleResolver`), `Paragraphs` (`ParagraphLayouter`), `Pages` (`DocumentLayout`, `PageFiller`, `Band`, `BlockPlanner`, notes, headers and footers), `Tables`, `Floats` (`ImageCache`), `Drawing` (`PageRenderer`)), `src/Raffica.Write` (the app, `AssemblyName` `RafficaWrite`, namespace `Raffica.Write`; references Core, Shell, Hosting, Model, Docx and Layout, never `Raffica.Pdf`), `src/Raffica.Hosting` (shared by both apps), `bench/write-layout` (`write-layout-bench`), `tools/gen-linebreak.cs`, `tests/Raffica.Write.Tests` (`Layout/*`), `tests/Raffica.Write.App.Tests` (assembly name as `InternalsVisibleTo` expects, namespace `Raffica.WriteApp.Tests`) and `tests/Raffica.Hosting.Tests`. Decision "Raffica Write: the layout library and the viewer (M4.2)" in `Docs/DECISIONS.md`.
- **Layout API:** `FontCatalog` (`CreateShipped`, `Resolve`; one per process, faces lazy and non-copy; order shipped and aliases, installed, shipped default), `LineBreaker` (own UAX #14, Unicode 18.0.0 table generated by `dotnet run tools/gen-linebreak.cs` and checked with `-- --check`, which CI runs; `third-party/unicode`), `DocumentLayout` (`Create(model, fonts, LayoutOptions(Mode: Pages | Flow))`, `LayOutFirstPage`, `LayOutThrough`, `LayOutRestAsync`, `Page(i)`, `Locate`, `BlockAt`, `IsComplete`, `FirstPageIsFinal`, `Revision`, `Notes`, `ReplaceModel`), `LaidOutPage` (immutable; its items are `PageItem`s: glyph runs, fills, rules, images, placeholders; `Text`, `Number`, `IsProvisional`), `PageRenderer.Draw(canvas, page, scale, ImageCache)`, `ImageCache`, `ImageRef` (id `<story>#<rId>`, stories `document`, `header:<relationship id>`, `footnotes`, `endnotes`; the app resolves them in `PackageImageSource`). Internal seams: `IBlockFlow` (`Height`, `Split(available, mustProgress)`, `Notes`), `BlockPlanner`, `IPageChrome`, and the `IWrapSource` and `IHyphenator` hooks of `ParagraphLayouter`.
- **Layout rules to remember:** tracked changes are shown accepted and comments not at all (4.6 adds the UI); whatever is not laid out is a marked placeholder, never dropped; the writing view is `LayoutMode.Flow` (strips, 520 pt wide, `LayoutRunner.FlowTextWidth`). A page with `NUMPAGES` or `SECTIONPAGES` is provisional ("…") until the layout is complete and is then replaced by a new object (`Revision` rises), so a view never keeps a `LaidOutPage` between frames and re-reads `Page(i)` when `Revision` changes. Pages are published by an array swap before the count is raised, one gate serializes laying out a page, readers take no lock. The hyphen is a glyph run with `IsHyphen` and an empty text range: hit testing, carets and text comparison must skip it. Lengths are points, colours `uint?` 0xAARRGGBB. `StyleResolver` must get `document.Numbering` as the third argument (the two-argument form silently drops numbering indents).
- **Prefix open and the first page:** `DocxFile.OpenPrefix(path or bytes, maxBlocks)` (`IsPrefix` only when the body was cut; cannot be saved; `DocxFile.Package` is the snapshot of the read, shared by the growth steps and `PackageImageSource`). **A prefix's `Body.FinalSection` is the section of the last block read, not the file's final section: use it for layout only.** The open order (`DocumentOpener` in the app, `FirstPageOpener` in the bench, because Layout cannot reference Docx): prefix of 64 blocks, page 1, growth 64, 512, 4096, whole file while `!FirstPageIsFinal`, then the full `DocxFile.Open` on the pool, `ReplaceModel`, `LayOutRestAsync`. `ReplaceModel` compares the text of page 1 and throws `InvalidOperationException` on a mismatch: the app then starts over with a new `DocumentLayout` and never calls `LayOutRestAsync` after a failed `ReplaceModel` (`LayoutRunner`). The levers and their measured effect are in the decision.
- **App (`src/Raffica.Write`):** `WriteWindow` (partials `.View`, `.Outline`) on the shell frame, `WriteTab` (owns the opened `DocxFile`, the layout, the `LayoutRunner` made on first access on the UI thread, the image source; `Disposing` event; `Docx` and `Layout` are replaceable, never cache them across `Runner.Changed`), `Documents/OpenFlow` (pure, `OpenResult`; only `OpenError.NotFound` removes a recent entry), `DocumentOpener` (pool thread), `LayoutRunner` (full open, `ReplaceModel`, `LayOutRestAsync`, throttled `Changed` events, `FullModelTask`, `EnsureFlow` for the strips), `Viewing/PageView` (page and writing view, zoom around the cursor, `FirstSharpPage`), `PageScroller` (pure scroll math in DIPs), `PageDrawOperation` with `DrawGate`, `ViewAnchor` (block and character, the character is always 0), `Panes/OutlinePane` and `OutlineSource` (outline level of the resolved paragraph, never style names), `Commands/*` (Write's own small catalog types, `WriteCommandRules` with a reason for every disabled command, `WriteRibbon`: Home `H`, View `V`), `Settings/WriteSettings` (default view and zoom mode), `Platform/MacOS/WriteMacMenu`, `Measurement`. Alt+Q is the command search (`SearchShortcut.AltQ` of `FrameKeys.Attach`, never Ctrl+Alt; ⌘K on macOS); Ctrl+K stays PDF's. `Render` reads `Page(i)` per frame and touches no visual (a first version invalidated a visual in the render pass). The page origin of a draw is rounded to a whole device pixel (the renderer snaps hairlines to it). The draw gate is closed (without blocking the UI thread) before the `ImageCache` is disposed; `ImageCache` has no eviction, byte budget or pixel cap and its first `Get` decodes on the render thread (an LRU, a cap and prefetch off the UI thread are due before 4.9, see the follow-ups of the decision). The pool-thread rule of the PDF section applies: `LayoutRunner` captures its dispatcher at construction. A key typed in the outline list belongs to the list (`InOutline`); the window forwards Page and Home keys only otherwise.
- **`Raffica.Hosting`:** `WindowHost`, `FileActivationBridge`, `AvaloniaFileActivationSource`, `InstanceHandover`, `RenderingChoice`, `CoalescingWriter`, `RecentService`, `DialogQueue`, `WindowSettingsSource<T>`, `WindowPlacementTracker` and the public `AppFiles` (`AppFiles.Pdf`, `AppFiles.Write`: names of the settings, recent and instance files and the config folder). - **Rules to remember:**
  - **One text definition.** `ParagraphProjection` defines the visible text and the offsets of a paragraph for the layout and the editor; every offset is a layout flat-text offset and a position is `TextPosition(StoryRef, Paragraph, Offset)` (endnote story key `endnote:<id>`). Undo and Enter replace `Paragraph` objects: re-read `session.Caret` and `Selection`, never cache a position across an edit.
  - **Incremental equals full.** `DocumentLayout.ApplyEdit` must give exactly what a fresh layout gives (`LayoutOracle.AssertEqualToFull`, exact equality, no tolerance; it drains the background chrome pass first, so a test that compares without draining sees stale pages by design). A new layout fast path needs a corpus oracle case first. Plan-cache and filler state keys include numbering and note state; a cached plan bakes in the section's text-area height (Forget on a geometry change); `PlanFor`, `Forget` and `Retain` run under the layout gate only. A header or footer edit takes the chrome-only path only when every page keeps its heights, parts and page-count use; stale pages are old immutable pages, never refreshed on read.
  - **Pages are read with `TryGetPage`** (`Page(i)` can throw after a truncation) and `Revision` is re-read per frame. Blank-space clicks never reach a header or footer (double click does).
  - **Every model change goes through the lease and `EditSession.Apply`:** one `BlockChange` per operation, `Changes[].OldBlocks` are read-only history snapshots, `EditHistory` clears itself after an edit behind its back. Select-then-delete: Backspace and DeleteForward over a field return `EditResult.Selected` and the caller deletes it next. A text delete never removes a paragraph break that carries a section break. The session is created on the first caret or key, never at open (`StartupCreatesNoEditorWork`).
  - **The lease:** `PauseForEdit` stops the background layout at a page end and holds the gate; a second request on the same thread throws, another thread waits (a `Monitor` on the runner's lock; the lease may be disposed on any thread); `LeaseWaitTimeout` is infinite in production and short in tests. A save takes it on the pool thread inside `DocxFile.BeforeModelRead` and releases it in `AfterModelRead` (finally on every failure); `BeginSave` is a UI-thread call, the handle may be disposed on any thread; typing and selection changes during a save are queued in arrival order. A failed `ApplyEdit` makes the session Faulted (Save disabled with a reason, Save as enabled); so does every operation exception except `StalePositionException`, the editor's own refusal of a stale position thrown before any change and the only plain refusal (`EditSession.MustFault`, shared by keys, commands and the replay of a save's queue; any other exception, `ArgumentException` and its subclasses included, may come after a change and before `Edits.Raise`, so the revision proves nothing); input a save dropped is counted and reported once through `EditSession.InputDropped`.
  - **Outline:** read on the UI thread (never a pool thread beside an edit), again 200 ms after the last edit (`WriteTab.ModelEdited`; no timer before the pane and the first edit), navigates by the heading's paragraph, not by a stored block index.
  - **History:** unique revisions (`DocumentEdits.Raise` is `++highest`), limits 1000 steps and 16 MiB (`HistoryLimits.Default`, pinned), typing coalesces per word.
  - **Clipboard:** formats `application/x-raffica-write-fragment` and `-source` plus text; `SourceId` and `SourcePart` decide whether relationship ids may stay (same story only). Fragment bytes are untrusted: `DocxFragment` scans first and enforces 8 MiB, 4 Mi characters, depth 64, 200,000 elements, 256 attributes per element, 100,000 attributes, 100,000 paragraphs, no DTD; an unreadable or refused fragment pastes as plain text and a fragment that flattens to nothing never deletes a selection. A fragment never carries comments, bookmarks or section properties. Cut replaces the clipboard only when the delete changed the document. A content control's content is a container like a cell: paragraph lookup (`TextEditor.FindIn`, `TextUnits.ContainerOf` and `IndexUnder`, `EditHistory` paths, anchors, copy) descends into tables and controls alike, a range across a control edge is refused, and a new block container must be added to all of them (`ContentControlEditingTests`, `RealEditorOracleTests` forced steps).
  - **IME:** the preedit lives only in the layout and never enters the model, the history or the revision; an edit during a composition cancels it (never rebase); the IME log holds lengths, never text; AltGr is text, never a command; the client is made on the first focus and the blink timer on the first caret. Tab belongs to the page view in a healthy document; F6 cycles panes, Alt+Q and Ctrl+Tab are the exits.
  - **Measuring:** `typing` is the worst p95 over all case and view pairs, 16.0 ms on every platform, judged on CPU cost (key handler, UI render pass, render-thread draws); the frame latency is recorded and not judged; the same line also carries the split of the judged time (`handler`, `render` = the UI render pass, `draw` = the render-thread draws) that `measure.cs` records as the unjudged family `typing-split`, and the Linux and macOS machine notes record the power state (governor, mains, temperature) a laptop's numbers depend on. Where the key handler's time goes is in the same rows (`ph-<phase>-median-ms` and `-p95-ms`: lease, operation, selection, layout, changed (the subscribers of `EditSession.Changed`), selection-event and rest), filled by `EditPhases` on the session, which only a measurement run sets. The case pickers `EditCases` (bench) and `TypingPlaces` (app) change together.
  - **Tests:** the 5 MB plain-text insert has a 5 s bound (1 s flaked under load); the blink test stops the timer and ticks by hand; xunit's `[Fact(Timeout)]` does not end a blocked UI thread, so gate tests use the lease timeout; `SaveFailureReason.TargetExists` is used for a target that appeared (tests keep "TargetAppeared" in the name).
- **Pitfalls found:** the Write tool and `.resx` edits make CRLF files and `dotnet format` fails: convert to LF; a keep-with-next walk-back must step back one page more than the carry record says; a cached plan and `NoteState.SameCounts` hide a changed note list when a reference swaps ids; a chrome refresh of a layout that is not complete must fall back when a part gains or loses `NUMPAGES`; an attribute or `xmlns` flood costs seconds before an element cap sees it (count `AttributeCount`); a relationship id of one story dangles in another; a corpus seed from `string.GetHashCode` is not reproducible (use FNV-1a); a UI-thread `PauseForEdit` (IME preedit, page-layout rebuild) while a save holds the lease on the UI thread throws, so the save takes it on the pool thread; `Render` must touch no visual; the headless typing run injects `TextInputEventArgs`, so the key-down path is separate.

- **Rules to remember:**
  - **Two kinds of edit.** Direct formatting is one `BlockChange` per operation through the lease and `EditSession.Apply` like typing; a style edit is a `StyleChange` step in `EditHistory` (old and new `Style` clone, identity swap in `StyleSheet.Replace`, never coalesced into typing). An `EditResult` with `Style != null` (also from undo and redo, unswapped snapshots) makes the session call `DocumentLayout.Restyle` **instead of** `ApplyEdit`, then rebuild the editor's `IEffectiveFormat` (`RefreshableFormat`). Restyle uses the existing `Restart` on a new `StyleResolver`: the resolver snapshots styles at construction, so a changed `Style` is invisible to an old engine.
  - **One definition of the effective value.** `LayoutEffectiveFormat` asks `StyleResolver`; a second layering implementation is not allowed. `EffectiveFormatTests` compares it with `BlockPlanner.PlanFor` for every run and paragraph of the corpus; a new layer in the resolver needs a case there.
  - **Property writing.** A value command merges attributes into the existing element (`s_themeAttributes`: `rFonts`, `color`, `ind`, `spacing`, with every legacy spelling) and children are placed by `SchemaOrder`; a spacing `line` needs its rule. Runs are split by Write's own run-level splitter (never `InlineSplitter`: it cuts hyperlinks and tracked changes) and merged afterwards only for Set, Toggle and Apply style; **a removal never merges** and equals "before minus that one element" (an emptied `rPr` or `pPr` stays), proven on the serialized XML by `OverrideRemovalTests` and the pane test `RemovingARowRemovesExactlyThatOverrideInTheDocument`. A toggle is judged on the effective value of the whole selection, tables and content controls between the ends included (depth 64).
  - **`LayoutEffectiveFormat` caches by revision.** The enclosing table cell of a paragraph comes from an index built by one walk of the story (`TableGeometry.Of` once per table), kept while `DocumentEdits.Revision` is the same and walked again once per revision for a paragraph it does not know; every restructuring edit raises the revision, so a hand-made model change that does not raise it is the one thing the index can miss. A per-run walk from the start of the story was quadratic and made select all on the thesis fail its 5 s bound in every full run. Commands read a paragraph through `EditSession.ResolveParagraph` (never a fresh `StyleResolver`: it has no table cell). A paragraph that is a block of its story (nearly every paragraph) is answered by a plain search and never earns a walk, and the index holds only the paragraphs in tables: a walk allocated 600 KB on the thesis, twice per formatting operation (every edit makes a new revision), so one bold toggle allocated 1.2 MB, which on the Linux laptop meant 27 gen 0 and 14 gen 1 collections in 100 keys and 170 ms of pause (now 26 KB per toggle; `EveryRunOfTheThesisIsReadFromOneWalkOfTheStory`). A paragraph in a table costs one walk per revision that reads no geometry (a dictionary of the table paragraphs), and the geometry of a table (`TableGeometry.Of`) is read on the first question about one of its cells, so a paragraph in one table never reads the others (the table-cell format case was 1.19 MB per key and the last one over 16 ms on the Linux laptop).
  - **Start of the Home band.** The Home band is about 3000 px wide, so every window starts compact: `RibbonTabDefinition.FullWidthAtLeast` (`WriteRibbon.HomeFullWidthAtLeast`, pinned against the real band in English and German) lets `RibbonView` choose compact at attach, before the first layout, and the Write app holds the band content (`RibbonView.HoldBand`, `WriteWindow` `deferRibbon: true`; tests keep it from the start) until two frames after the first sharp page; key tips, the command search and `OpenPicker` release it at once. A new command or group must keep the hint at or below the real width (`RibbonStartupTests`); never measure or template the full Home band at start (the cost was 50 ms of the first page). `Docs/DECISIONS.md`, "The start cost of the Home band".
  - **Bounded reads, cached.** Facts, the Home display and the inspector read at most `TextEditor.MaxFactBlocks` (200 top-level blocks); beyond it facts are permissive, the display is all mixed and the pane says "too large". Answers are memoized by model, `Edits.Revision` and range (`ReadFormatFacts`, `ReadSelectionFormat`, `ReadInspector`; counters `FactReads`, `InspectorReads`); nothing is read before a session exists or before the command is asked. A new subscriber of `EditSession.SelectionChanged` (it fires per typed character) must debounce through `FormatDisplayRefresh` or stay trivial. A hidden pane detaches and cancels (`Hidden`, `Shown`). The view's own change event (every key) updates the status text at once but asks the ribbon's commands only through `ViewStatesRefresh` (100 ms debounce, made on the first change after the tab has an editing session): a refresh of every command per key was 4 to 5 ms of the key handler on the laptops (`TypingDoesNotAskEveryCommandOfTheRibbonForEveryKey`).
  - **Payload commands and pickers.** `format.font`, `size`, `sizeUp`, `sizeDown`, `color`, `highlight`, `spaceBefore`, `spaceAfter`, `lineSpacing`, `paragraphStyle`, `characterStyle` are catalog entries run through `WriteWindow.RunCommand(id, payload)` (bad payload: false, never an exception; contract in the decision); a picker has no `Run` (the command search opens it by `RibbonView.OpenPicker`); `PickerDefinition.Items` is a lazy `Func` (fast, non-null, non-throwing; asked on every open, never at ribbon build: `StartupCreatesNoPickerWork`). `WriteCommandCatalog.Find` skips `format.*` (the page view owns Ctrl or Cmd with B, I, U, E, L, R, J; AltGr is text). Every new command needs its own Lucide icon, a reason in every disabled state (`FormatCommandTests`), strings in both languages and a line in `WriteMacMenu`; `FmtRow*` keys are guarded by the wording test, a new `pPr` or `rPr` element Write should name needs wording in both languages.
  - **Pending format** is session-only (never in the model, history or revision), survives typing, is cleared by a selection change, any non-typing operation and Esc; `EditResult.KeepSelection` keeps the selection across a format operation. **An IME commit takes it only when it is the very object the session had when the composition began and still has** (`PageView.Ime` captures `session.Pending.Changes` at the first preedit, `OnTextInput` compares with `ReferenceEquals`): Ctrl+B, then composing, gives bold text; a format set or cleared during the composition is dropped. The IME check doc has the steps.
  - **The pane acts on the current selection:** a remove button flushes the pending refresh first, so a stale row cannot act on a new selection; the app reads with `TextEditor.Inspect` (editor hosts), never the plain-host `FormattingInspector.Read`.
  - **Measuring:** `format` is the worst p95 over all case and view pairs, 16.0 ms on every platform, judged on CPU cost like `typing`; `typing-pane` rows (`typing/pane-*`) count into the `typing` metric and `typing-refresh/*` rows (the debounced refresh body) are recorded and never judged. A style update is recorded, not judged.

- **Rules to remember:**
  - **Blank document and untitled tabs.** The style set is 24 ids (`BlankStyleSet.Ids`; not 33), headings are outline levels 0 to 8 with no `numPr`, body Carlito 11 pt, headings Caladea, A4 with 2.5 cm margins (Letter with 1 inch for the regions US and CA, `BlankPaper.For`); the bytes are deterministic and the document language and the dates are fixed. A tab with no path is untitled: `WriteTab.Path` is `string?`, so every new consumer of the path must be null-safe; Save on it is Save as, it is never in the recent list, and a restored tab is the same kind with `SuggestedSavePath` set. `file.new` is Ctrl or Cmd with N and must keep the Home band's width hint; nothing of the blank document exists before first use (`StartupCreatesNoBlankDocumentWork`).
  - **A recovery copy is the pair `<id>.docx` and `<id>.json`**, the id 32 lower-case hex digits, in `<AppFiles.ConfigDirectoryFor(settingsFile)>/recovery`; **the sidecar is the commit marker** (the DOCX is written first, the sidecar second; a DOCX with no sidecar is never listed), holds the owner's process id and start time and **never document text** (no text in a file name, a log line or an exception message); `Delete` removes the DOCX first; a sidecar is untrusted. An entry whose owner is alive and not this process is never offered and never deleted (`RecoveryLiveness`; alive with an unreadable start time counts as live). Tests and measurements get their own folder through `--settings-file`.
  - **A snapshot is `RecoverySnapshot.WriteAsync`, UI thread only** (the in-flight mark is set there; the process identity, the folder and the sidecar look-up run on a pool thread; the folder is made 0700 on Linux and macOS), through `DocxFile.SaveSnapshotAsync` under the **model-read lease** (`ModelReadLease.Attach`, shared with `WriteSaveFlow`: the pool thread takes the editing lease inside `DocxFile.BeforeModelRead` and releases it in `AfterModelRead`). It never calls `MarkSaved`, never touches the origin, stamp or snapshot of the file, never throws and never shows anything. **One writer per `DocxFile`:** a per-file in-flight marker (`IsRunning`, `WhenIdleAsync`) serializes a snapshot against a save and against another snapshot because they share the two hooks; `WriteSaveFlow.WriteAsync` awaits an idle file first. Whatever a pool thread reads inside the lease must be thread-safe state (`IInLeaseSnapshotCheck`), never a collection the UI thread changes.
  - **The block cache.** `BodySnapshotCache` keeps the bytes of each top-level body block; correctness depends on the **attribution rule: every `DocumentEdits.Raise` or `Restore` is followed by `DocumentEdits.Attribute(changes)`** with the edit's `BlockChange` list (the editor does it at every raise site, in `Undo` and in `Redo`); a raise that was not attributed, a failed pass or an unseen block makes the pass write the whole body (slow, never wrong). A new raise site in the editor needs an attribution and a case in `SnapshotCacheOracleTests` (byte equality with the user-save writer's main part). The user's Save and Save as never read the cache and keep the full guard; **a copy has a lighter guard** (chunked byte compare of every model part, the main part read back as well-formed XML with a `w:document` root instead of as a model, a deliberate trade for GC load: a writer bug can now replace a good older copy with one that does not open as a model), pinned by `DocxSnapshotGuardTests`.
  - **The scheduler.** One `AutosaveScheduler` per window, made when the first tab becomes dirty (never at start), beat 30 s (`AutosaveScheduler.Interval`), `TickNow` on deactivation, one snapshot at a time, the last written revision tracked by the scheduler itself, skips without a trace (closed, prefix, faulted, saving, busy), a failure is counted and retried and never shown; the setting `ShellSettings.Autosave` is read live at every tick and shown under Write's own label (`SettingsDialogOptions.AutosaveLabel`; the shell's text would say the file is saved). A copy is deleted when its tab is clean again and when its tab is released **after the close questions were answered Save or Don't save**; a Cancel, a bare dispose or a window close keeps it (offered at the next start). Never in a measurement run (`WriteWindow.OnTabDirtyChanged`), and the wiring is in a try/catch (`RecoveryWiringFailures`): autosave must never break typing. Nothing of the store, the clock or the folder exists before the first dirty tab (`StartupCreatesNoRecoveryWorkTests`).
  - **The offer.** Once per process (`RecoveryCoordinator.OfferOnce`, one coordinator held by `App`), after the first sharp page of the first window or after `Opened` for a window with no file (also for a window whose file failed to open), never while measuring or closing; one `RecoveryCard` (Restore, Discard, Later, Esc is Later; at most 20 named, never text from the document). Restore opens each copy as a **dirty, unbound tab** (`OpenFlow.OpenRecoveredAsync`; Save is Save as with the old name suggested), adopted under the entry's id **before** the dirty mark (`AutosaveScheduler.Adopt` needs `subject.Id == existingId`, so build `new WriteTabRecoverySubject(tab, entry.Id)`); the copy stays until Save or a Save or Don't save close. Discard deletes exactly the offered entries on a pool thread; a copy that cannot be opened is kept and reported in one card for all of them, worded as the recovery copy that cannot be read (`recoveryCopy` of `OpenErrorCard`, `recoveryCopies` of `OpenFailuresCard`); shown names go through `WriteWindow.ShortName` (no split surrogate pair). A new card factory must be listed in `CardFooterTests.Entries` **and** in the expected list of `CloseGuardTests.CardsAreBuiltByCardFooter` (the second was missed once).
  - **The picture cache.** `ImageCache` has a budget of 256 MiB of decoded pixels (4 bytes per pixel) and a cap of 32,000,000 pixels per picture (`ImageCacheLimits.Default`; the cap is at most half the budget, pinned), least-recently-used eviction into a retired list that **only `ReleaseRetired` disposes, called after each draw inside the draw gate** (`PageDrawOperation`). The app's cache is made with `decodeOnGet: false`: **the render thread calls `TryGet` and `ReleaseRetired` only and never decodes**; page 1 is decoded in the opener (`Warm` with the open's token) and the pages in view and one each side are prefetched by `PageView` from `RaiseViewChanged`, one task at a time, latest range wins, a picture not ready is the marked box and one coalesced invalidation follows the decode. `PackageImageSource.Read` is called from pool threads and stays thread-safe. **A future insert-picture feature must call `ImageCache.Clear` and trigger a prefetch.** A prefetch restarts from `PageView.PrefetchEnded` only after a cancelled task (a completed task is never followed by another: a range above the budget would decode forever). The bench, tests and pixel oracle call the synchronous `Get`.
  - **Measuring.** `typing-snapshot` types while snapshots run back to back (3.5 a second, harsher than the real 30 s cadence); its rows count into the judged `typing` metric (16.0 ms), the lease and total times of a copy (`snapshot/*` rows) are recorded and never judged; a quiet machine is needed (a noisy one doubled plain typing).
- **Pitfalls found:** a snapshot overlapping a save on one `DocxFile` clobbered the shared `BeforeModelRead` and `AfterModelRead` hooks and could fail the user's save; a check on the pool thread that read `WriteSaveFlow`'s dictionary was a data race no test can show; the owner probe mapped "alive but start time unreadable" to dead, which broke the live-owner rule; `Delete` that removed the sidecar first orphaned an undeletable DOCX; a `Lazy` that caches a throwing `Process.StartTime` made every later snapshot fail; the guard's read-back of the main part into a model cost 20 MiB per copy and, at 3.5 copies a second, 100 gen2 collections and 11.4 s of GC pause in one run (the cause of most of the remaining p95); the prefetch skip key `(layout, range, count)` hid a picture that an edit or undo moved into view; `CloseGuardTests.CardsAreBuiltByCardFooter` has its own expected list of card factories; tests with hard-coded `C:\` paths failed on Linux and macOS (use `Path.Combine` with the fixture folder); several corrupt copies queued one error card each at every start; a first copy that fails in the sidecar write must delete the DOCX it just made; the Write tool and `.resx` edits make CRLF files and `dotnet format` fails on them (convert to LF); an AOT publish needs the `Microsoft Visual Studio\Installer` folder on `PATH` and its log is searched for `IL[23][0-9]{3}`; the killed-process test needs the harness built (`dotnet build Raffica.slnx -c Release` first; it fails with that message, it never skips).
- **Known limits (details in the decision):** a crash between the two writes of a first copy leaves an orphan DOCX (unlisted, not cleaned), and a process killed mid-write leaves its temporary DOCX or sidecar (`AtomicFile.NewTemporaryPath` puts it in the recovery folder, so it holds document text, unlisted and never removed; both for the 4.9 sweep); Cancel on a later tab keeps the copies of earlier Don't-save tabs; a restored copy's sidecar keeps the dead owner's pid until its first snapshot; the offer-once flag is claimed before the card is answered; the 50-tab restore cost is unmeasured; own-process copies are offerable; the first copy of a session or after an unattributed edit writes the whole body inside the lease (about 13 ms once); the document language is a fixed `en-US` and the dates are fixed at 2026-01-01; bullets use Symbol and Wingdings glyphs that may draw as a fallback until 4.4; a reused picture id needs `ImageCache.Clear` and a prefetch (rule for the insert-picture feature); `BodySnapshotCache` keeps every block's bytes and a `MemoryStream` whose capacity never shrinks for the life of the `DocxFile` (2 to 3 times the serialized body); `RecoveryLiveness.IsLive` treats an unreadable start time as live, so after a crash and a reboot a copy whose old pid now belongs to a protected process is not offered until that process ends; a snapshot in flight at `Release` deletes the copy later in the `AutosaveScheduler` `StepAsync` continuation, so if the last window closes and the process exits first, the copy of a Don't-save document is offered at the next start (privacy nuisance, not a loss); the macOS menu's New item is a plain `Item` (`NewDocumentAsync` re-checks `IsClosing`); a layout fault of an untitled tab shows no card, only the disabled Save and Save as with their reason; the killed-process harness's `PrintNewCopy` records the write at lease time and the second test rarely kills mid-write; the crash guard is not part of 4.3c (it moves to 4.9 with an orphan sweep).
- **Owner gates of 4.3c (all open; milestone 4.3.3 stays `in-progress`):** **Word** opens a blank document and a restored copy (rows in `Docs/write-word-check.md`, section "New document and recovery (milestone 4.3c)"); kill and restart on a real display on Windows, the Linux laptop and the Intel Mac; the autosave box and the 54-character German label on a real display; `typing` and the start cases on the Linux laptop and the Intel Mac (`gh workflow run measure.yml --ref <ref> -f platform=<windows|linux|macos> -f target=write -f note="<machine>" -f ref=<ref>` and `write-layout-bench edit --snapshot --file testdata/write-corpus/thesis/thesis.docx` on a Native AOT publish; the Windows PC measured a worst p95 of 9.83 to 12.37 ms on a noisy day against 16.0); **the owner decides** whether the back-to-back reading of `typing-snapshot` stands. The 4.2, 4.3a and 4.3b gates stay open.

## Maintaining the roadmap

The source of truth is `Docs/roadmap.json` (schema: `Docs/roadmap.schema.json`). `Docs/ROADMAP.md` is generated from it and never edited by hand. The .NET 10 SDK is required, even if the project otherwise uses a different stack.

1. Edit only `Docs/roadmap.json`: status, plan link, tick tasks and criteria (`"done": true`, proof in `"evidence"`), scope changes, backlog. Leave optional fields out, never set them to `null`.
2. Then run `dotnet run tools/roadmap.cs -- generate` and commit both files. Errors name the path in the JSON (for example `subprojects[0].milestones[2].completedOn`).
3. `dotnet run tools/roadmap.cs -- check` validates the schema and references and checks that `ROADMAP.md` is up to date; the CI (job `roadmap`) does the same.
4. Rules: `status` is `open`, `planned`, `in-progress` or `done`; `done` requires `completedOn` (YYYY-MM-DD), from `planned` on `plan` is required (path relative to `Docs/`); milestone ids are unique strings (`"5.1"` is allowed); prerequisites and `afterMilestone` must exist; title, goal and name are a single line; texts are Markdown; whatever fits nowhere goes into `blocks` (`title`, `text`).
5. A new milestone is an entry in `subprojects[].milestones`:

```json
{
  "id": "1", "title": "<title>", "status": "open",
  "prerequisites": ["0"],
  "goal": "<One sentence: what is possible after this milestone?>",
  "tasks": [ { "text": "…", "done": false } ],
  "acceptance": [ { "text": "… (verifiable: test, command or a concrete manual check)", "done": false } ]
}
```

   A new subproject is an entry in `subprojects` (`number`, `name`, `spec` with `text` and/or `link`, `milestones`), a release is an entry in `releases` (`version`, `title`, `status`, `afterMilestone`, optional `covers`, `date`, `intro`, `acceptance`, `blocks`).
6. Ideas belong in `backlog` (`title`, `text`, optional `idea`). The skill `/ideen` (from `benjo-code/Labjo`) enters adopted ideas there and regenerates `Docs/ROADMAP.md`.

## Milestone workflow

Every change "in the roadmap" (link a plan, set a status, tick tasks, scope changes) is a change to `Docs/roadmap.json` together with the regenerated `Docs/ROADMAP.md`, see "Maintaining the roadmap".

**"Plan milestone N":**
1. Create the branch `feature/mNN-<topic>` from the current `dev`. Plan, roadmap maintenance and implementation of the milestone all go through this branch.
2. Read `Docs/ROADMAP.md`, the spec of the subproject and the current state of the code.
3. Review the project's open ideas with `/ideen` (skill from `benjo-code/Labjo`, installation: `bash tools/install-ideen-skill.sh` there): adopt, implement or discard. Whatever belongs in the milestone flows into the plan. The roadmap change lives on the milestone branch (when asked, choose "current branch").
4. If the milestone starts with "Create spec" or the subproject has no spec yet: first work out the spec with the user by brainstorming and put it under `Docs/superpowers/specs/`.
5. Write the plan to `Docs/superpowers/plans/YYYY-MM-DD-milestone-NN-<topic>.md`. The plan covers exactly the tasks and acceptance criteria of the milestone, nothing more.
6. In the roadmap, link the plan and set the status to `🟡 planned` (overview table and milestone).

**Implementation:**
- Status `🔵 in progress`. Tick every finished task in the roadmap right away.
- Tick acceptance criteria only once they have actually been checked, and note the proof behind them (test name, command + result or manual check).
- At the end, status `✅ done` with the date in the table and the milestone, then a PR to `dev` (see "Git & branches").
- Record scope changes in the roadmap under "Scope changes", not silently in the code.
- Work only within the scope of the active milestone. Do not anticipate features, packages or architecture decisions of later milestones.

## Git & branches

- `main` contains only published states (releases). `dev` is the integration branch.
- Always work on `feature/<topic>` or `fix/<topic>`, branched from the current `dev` (`git switch dev && git pull && git switch -c feature/<topic>`).
- Before any work, check `git status` and the current branch. If on `main` or `dev`, create a feature branch first. Never commit directly to `main` or `dev`.
- Feature and fix branches go to `dev` via PR. Claude merges these PRs itself once the work is finished and all CI checks are green (squash merge allowed).
- PRs to `main` exist only for releases and hotfixes and only on the explicit instruction of the user.
- PRs between `main` and `dev` (release, hotfix, returning `main` → `dev`) are always merged with **"Create a merge commit"**, never by squash or rebase. Otherwise `main` and `dev` lose their common history and every release causes conflicts.
- Hotfix: branch `hotfix/<topic>` from `main` → PR to `main` → release (see below) → then merge `main` into `dev` via PR.
- Stage selectively (`git add <file>`). No `git add .` or `git add -A` if foreign changes that do not belong to the task are in the working tree. For files that were already modified before, read `git diff <file>` first and use `git add -p` if needed.
- After every commit, check `git show --stat HEAD` against the expected file list.
- Commit messages follow Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`, `ci:`, optionally with a scope (`feat(api): …`).
- Forbidden without explicit instruction: force push, `git reset --hard`, deleting branches, rewriting history, bypassing hooks with `--no-verify`.
- Always create new repos (including companion ones like `-Releases` or `-Privacy`) in the org `benjo-code`, always with the owner spelled out (`gh repo create benjo-code/<name> …`), never under the personal account. Then check with `gh repo view benjo-code/<name>`.

## Releases

- Versioning follows SemVer (`vMAJOR.MINOR.PATCH`).
- `CHANGELOG.md` → `[Unreleased]` is extended in every PR with a change worth mentioning for users (not for pure planning, roadmap or internal cleanup PRs).
- Procedure (only on instruction):
  1. Branch `release/vX.Y.Z` from `dev`, turn `[Unreleased]` in `CHANGELOG.md` into `[X.Y.Z] – YYYY-MM-DD` (name the included milestones) and add a new, empty `[Unreleased]` above it.
  2. PR `release/vX.Y.Z` → `main` (merge commit).
  3. Tag and GitHub release in one step: `gh release create vX.Y.Z --target main --title "vX.Y.Z" --notes "<CHANGELOG section>"`.
  4. Return `main` to `dev` via PR (merge commit) so the two do not drift apart.

## Project memory

- Document anything important for the future in the repo without being asked:
  - Architecture and technology decisions, fixed versions, rejected approaches → `Docs/DECISIONS.md`
  - Scope changes → `Docs/ROADMAP.md`, section "Scope changes"
  - Lasting project knowledge (architecture, conventions, workarounds, pitfalls) → this file, section "Project-specific"
- Do not record guesses, intermediate states or temporary diagnoses as facts.
- References name the file and the type, member or section, never line numbers (they go stale).

## Quality & proof

- "Done" means: build, test and format/lint (commands above) are demonstrably green. Name the command and the result.
- `dotnet run tools/roadmap.cs -- check` is part of "done": the roadmap is valid and `Docs/ROADMAP.md` is up to date.
- Whatever could not be verified (for example because real hardware or credentials are missing) is explicitly marked as open, together with the command that checks it.
- Do not suppress warnings, skip tests or weaken checks just to make something green.

## Security

- No secrets (tokens, passwords, keys, real credentials) in files, commits, logs, PRs or replies.
- Never quote or print values from `.env` or similar, only variable names or placeholders.
- Secrets come from env vars or a secret store. Keep a placeholder in `.env.example` for every required variable. `.env` is in `.gitignore`.

## Collaboration

- Ask when requirements are unclear instead of guessing.
- Destructive actions or actions with external effect (merge to `main`, release, deleting branches, tags, releases or repos, changes to GitHub settings) only on explicit instruction. Feature branches that are deleted automatically after the merge are excluded.
