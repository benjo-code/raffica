# Milestone 2.4 – Organize pages: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Raffica PDF reorders, rotates, deletes, duplicates and inserts pages (blank pages and pages of other files, which is how files are merged) in the pages pane and the ribbon, applies the plan as a checked full rewrite after showing what the rewrite loses, splits a document and extracts pages into new files, and exports pages as PNG images.

**Architecture:** Core already holds everything below the UI and the command line already uses it: `PageEditPlan` (immutable plan of `PageSlot`s: `Rotate`, `Delete`, `Move`, `Duplicate`, `InsertBlank`, `InsertFrom`, `FollowPage`), `PageEditHistory` (undo and redo of plans), `PageEditExecutor.AnalyzeAsync` (the `PageEditReport` of `PageLoss`es, `IsRefused`), `PageEditApplier.ApplyAsync` (working copy from the file, checked atomic rewrite through `DocumentSaver`, adoption into the `ViewerSession` with a new cache), `DocumentSplitter` (`SplitMode.Every/Ranges/Bookmarks`, `Plan`, `Extract`, `AnalyzeAsync`, `TargetPaths`, `WriteAsync`), `PageImageExporter.ExportAsync`, `OutputNames`, `PageRange` and the limits (`PageEditLimits`). The CLI commands `rotate`, `merge`, `split` and `export` use them and `Raffica.Cli/Commands/PageLossText` words the losses in English. 2.4 adds the app side only: a per-tab `OrganizeSession` (history, inserted files, selection, locks), an organize mode of the pages pane, a Pages ribbon tab, the insert-file flow, the Apply card with the loss list, the rebuild of a tab after a rewrite, the close and save hooks, and the cards for extract, split and image export. Logic without a window is plain classes tested without Avalonia; controls are tested headless as in 2.1 to 2.3.

**Tech Stack:** .NET 10 Native AOT, Avalonia 12.1.4, xunit.v3 3.2.2 with `Avalonia.Headless.XUnit` (as `tests/Raffica.Pdf.Tests`), Core only for PDF work; no new package.

**Spec:** [Docs/superpowers/specs/2026-11-04-raffica-pdf-design.md](../specs/2026-11-04-raffica-pdf-design.md): sections 2 to 4 and 6 (saving, full rewrite for page operations with the warning for signed files), 7 (row 2.4), 8, 9. Frame rules: "App frame conventions (M1.2)", "Raffica PDF: viewer conventions (M2.1)", "annotation conventions (M2.2)" and "forms and signing conventions (M2.3)" in [Docs/DECISIONS.md](../../DECISIONS.md). Behaviour rules come from the predecessor's spec `2026-10-31-teilprojekt3-seiten-design.md` (read-only checkout `C:\VS-Code\Pagewing`, tag `v1.0.0`, read with `git show`; German); the rules a task uses are cited in English in that task. Where this plan departs from them it says so under "Calls made while planning".

## Global Constraints

- **Stack and layering:** `Raffica.Pdf` references `Raffica.Core` and `Raffica.Shell` only and knows no PDFium type. Every Core call is awaited, the UI thread never waits for PDFium. `PageEditApplier.ApplyAsync` must run on a pool thread (it reads file stamps and the adoption closes the old document); its `IProgress<double>` and `ViewerSession.Changed`/`PagesInvalidated` arrive on other threads: marshal to the UI thread before touching a control or `PdfTab`. `AdoptRewrittenDocumentAsync` must never be called from a handler of `Changed` (Core remark).
- **Never damage the original (spec 2):** the rewrite is Core's checked, atomic one; the app never writes a PDF itself. Any failure before the target is replaced leaves the target byte for byte as it was and the plan open in the pane, so the user never loses pending changes to an error. No backup copy is made (that would be a silent write); "Save as…" is the way to keep the original.
- **Say it before, never lose silently (predecessor's decision):** every loss of `PageEditReport` is worded in the Apply card before anything is written; `IsRefused` is honoured (nothing is written, the reason is shown, the plan stays). The CLI text is the model for the wording, not the UI text. No UI text calls a signature "valid" or anything "legally binding" (the guard test `NoUiTextCallsAnythingLegallyBinding` covers the new texts in both languages).
- **Look:** direction D, PDF ink plum, shell tokens and controls only, no hex literal in a component style (`NoHexInComponentStylesTests`). A pending change is never shown by colour alone (an icon plus text, with an automation name). A new colour token is not planned; if one becomes necessary, the checklist in `CLAUDE.md` section "Shell" applies. The destructive command (Delete pages) sits in the separated destructive group at the end of its tab, as the canvas has it.
- **Strings:** every UI string in `Strings.en.resx` and `Strings.de.resx` of the app project with an accessor in `PdfStrings`; `TranslationTests` and `CommandCatalogTests` must stay green.
- **Startup (spec 5):** nothing of 2.4 is created before the user uses it: no `OrganizeSession`, no inserted-file document, no card and no thumbnail source of an inserted file at start or at the first sharp page (test). Measurement runs (`--measure-*`) stay unchanged and the speed budgets are not touched; the organize mode of a 1000-page file is measured as information only (Task 12).
- **Hostile input:** the Core limits apply and are tested through the UI path: `PageEditLimits.MaxSlots` (20 000 pages in a plan), `MaxInsertedFiles` (20), `PageImageExporter.MaxPixels` (64 megapixels per exported page), a range text of any shape, a corrupt inserted file, a file that is the open document itself. Every refusal ends in a card with its reason and no change.
- **Not in this milestone:** crop, watermark, header and footer, page numbers, editing page labels, images as new pages, JPEG export (Core has a PNG encoder only), a merge dialog with a file list, dragging pages between tabs or windows, editing metadata, flowing unsaved annotation or form changes into the working copy (the card asks to save first), renaming duplicated form fields, a plan-to-new-file writer ("Save selection as…" of a plan), redaction, OCR, installers, macOS.
- **Done** means: `dotnet build Raffica.slnx -c Release` (0 warnings), `RAFFICA_REQUIRE_OCR=1 dotnet test Raffica.slnx -c Release --no-build --max-parallel-test-modules 1`, `dotnet format Raffica.slnx --verify-no-changes` and `dotnet run tools/roadmap.cs -- check` green, each acceptance criterion with its proof in `Docs/roadmap.json`. Local builds may need `-p:NuGetAudit=false` (known advisory, see the 2.1 evidence).
- **Commits:** Conventional Commits with the trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; stage files by name; `git show --stat HEAD` after each commit; noreply address only. Branch `feature/m24-organize-pages`; PR to `dev` at the end, merged when `ci` and `roadmap` are green. Tick roadmap tasks as they finish (`dotnet run tools/roadmap.cs -- generate`). Tests that write work on temp copies of the fixtures, never on `testdata`, never to the real user folder.

## Calls made while planning (author's calls, the owner can overturn them)

1. **One plan, nothing written until "Apply" (predecessor's decision, kept).** Changes are pending in the pages pane; the page view keeps showing the unchanged document until Apply, because annotations, search, forms, layout and caches hang on page numbers of the open file. The pane's organize mode is entered and left by a command; leaving with a non-identity plan asks (apply, discard, back).
2. **Locks while a plan is open.** Annotate tools, the Sign command, form filling, Extract, Split and Export images are disabled with the visible reason "Apply or discard the page changes first" (the export reads the open document without the plan, so a plan open would give pages that do not match the list). Print stays enabled (it prints the open document, which the pane says). Save (Ctrl+S) and Save as with an open plan open the Apply card.
3. **Unsaved annotation or form changes are saved first, with a question.** Apply with `tab.Annotations.Editor.IsDirty` asks "Save the marks and form values first?" ("Save first" default, "Back"); the incremental save runs through `SaveController`, then the rewrite. Flowing the history into the working copy is not built (predecessor: backlog). Wording for an open unresolved draft: the same card refuses ("Finish or discard the open edit first").
4. **The Apply card shows summary, losses and the way out.** "12 → 10 pages, 3 turned, 1 file inserted", the localized loss list per `PageLossKind` (including `SignatureInvalidated` for a signed file, DocMDP level from `Detail`), one sentence that a rewrite cannot be undone, and three buttons: "Save as…" (default, focused), "Save in the original file" and "Back". An `IsRefused` report shows only the reason and "Back".
5. **Tab rebuild after the rewrite.** `PageEditApplier` makes the `ViewerSession` adopt the new document with a new cache, but `PageView`, the pages and marks panes, the marks model, the form session, the search, the text selection and the outline are all bound to the old page list and (for a rotation) the old page sizes. The app therefore rebuilds the per-tab pieces of the tab after a successful apply: it disposes them, drops them from the window's dictionaries (the same cleanup as closing a tab, without the tab) and lets `ShowActiveView` build them again over the adopted document, at the page `PageEditPlan.FollowPage` gives (clamped) and the previous zoom and layout. The annotation and form sessions are made anew (the editor of a rewritten document starts clean). Fallback if the rebuild proves unsafe in Task 2: close the tab and open the written file as a new tab in the same strip position; the user-visible result is the same and the test names stay.
6. **Pages of inserted files show real thumbnails.** One `ThumbnailSource.Create(document)` per inserted file, made when its pages first appear and disposed when the mode ends or the file's last slot is gone; blank pages are drawn (paper and the size), not rendered. Cheap to change: only Task 4 decides.
7. **Merge is "Insert file…".** Choosing a file, an optional range (`PageRange` syntax: `3`, `2-5`, `1,3,5-7`, `all`) and the position (after the selection, else at the end) adds the pages to the plan; repeated, this is the merge of any number of files. The predecessor's own merge dialog with a file list stays out (its backlog). The first file is the main file (its bookmarks, form, page labels and information stay); the card says what the other files lose before Apply, through the report. `raffica merge` is unchanged.
8. **Reordering:** drag with an insertion marker, and the keyboard: Alt+Up and Alt+Down move the selected pages by one position, Alt+Home and Alt+End to the first and last position; Delete deletes, Ctrl+D duplicates only inside the list, rotation has ribbon commands and `[`/`]` keys inside the list. The list keeps its Tab behaviour (Tab never traps focus). All keys are list-local, none is a catalog shortcut (so no new window-level key capture); the ribbon commands are the catalog.
9. **Undo and redo:** while the mode is active and the list or a ribbon command has the plan, Ctrl+Z / Ctrl+Y (and the Undo and Redo commands) go to the plan history, never to the annotation history (which is locked and clean by call 3). Outside the mode they behave as in 2.2.
10. **Extract, Split and Export images read the open document without a plan** and are ranges-in-a-card: the card has a range field (`PageRange` syntax) preset to the current page (extract), "all" (export), or a split mode (every n pages, ranges `1-3,4-9`, bookmarks of the top level). They write new files into a folder the user picks, never replace an existing file (`overwrite: false`; a name clash is named in the result), show the loss list per part where the report says something (`DocumentSplitter.AnalyzeAsync`: every part invalidates the signature of a signed file) and run as a job with progress and Cancel through the existing job card pattern. After a single-file extract the result card offers "Open", otherwise "Show folder" is not offered (no platform code in this milestone) and the folder path is shown as copyable text.
11. **Image export:** PNG, resolution 72, 150, 300 dpi or a custom value (scale = dpi / 72), annotations and form fields on or off, always the light page, names `<stem>-p<NNN>.png` as `raffica export` writes them. A page over `PageImageExporter.MaxPixels` is refused before the first file is written, with the page named.
12. **A Pages ribbon tab, letter P** (if the test `RibbonDefinitionTests` finds the letter or a field code clashing, use `O`), five groups: Organize (enter and leave the mode), Edit (rotate left, rotate right, duplicate, blank page, insert file, move up, move down), History (undo, redo), Apply (apply, discard) and, set apart at the end, the destructive group (delete pages). Extract, Split and Export images sit in a sixth group "Output". Stand-in icons as in the other tabs.

## Review Focus

1. **Apply then immediately close, save or print.** Expected: the apply job finishes or is canceled before anything else uses the document; the tab is dirty while a plan is open and clean after a successful apply; close with an open plan asks "Discard the page changes?" (Save is Apply). Pinned by `OrganizeCloseTests.CloseWithOpenPlanAsksAndDiscardKeepsTheFileUntouched` (Task 8).
2. **A failing or canceled rewrite** (changed source file, target exists elsewhere, encrypted file refused, disk full, user cancel). Expected: the target is byte for byte as it was, the plan and the selection stay, a card names the reason. Pinned by `ApplyFailureTests.EveryFailureKeepsTheFileAndThePlan` (Task 7).
3. **Rotation only, same page count.** Expected: the rebuilt view shows the rotated page sizes (a rebuild that only compared the page count would show stale sizes). Pinned by `TabRebuildTests.RotatedPagesGetNewSizesAfterApply` (Task 2).
4. **Signed, encrypted and form files.** Expected: the Apply card lists the signature loss for `signed-docmdp-*` (no word "valid"), the refusal for an encrypted file inserted into an unencrypted one, the field-name collision and duplicated form fields for `forms-basic` copies. Pinned by `ApplyCardTests.LossesAreWordedPerKind` and `ApplyFlowTests.EncryptedInsertIntoPlainIsRefused` (Task 7).
5. **Hostile plans and ranges:** a plan of 20 001 pages, 21 inserted files, a range `0`, `5-2`, `999999999`, a corrupt inserted file, the open file inserted into itself, the last page deleted. Expected: a card with the reason, the plan unchanged. Pinned by `InsertFileTests.EveryRefusalEndsInAReasonAndLeavesThePlan` and `OrganizeSessionTests.LastPageCannotBeDeleted` (Tasks 3 and 6).
