# Raffica Write 4.5a: tables, pictures, footnotes and endnotes (design)

Status: approved by the owner, 2026-11-24 (with clipboard paste of pictures added to the scope). Milestone 4.5.1 of `Docs/roadmap.json`. The subproject spec is `Docs/superpowers/specs/2026-11-13-raffica-write-design.md` (section 6, "Long-document tools" and "Editing what a file already contains"); this document only settles how 4.5a builds what that spec already decided. 4.5b (bookmarks, captions, cross-references, tables of contents) and 4.5c (hyperlinks, the macOS search key, find and replace) come later and are not built here.

Items marked **(call)** are decisions of the author of this document, not of the owner. The owner decided on 2026-11-24: the old 4.5 is split into 4.5a, 4.5b and 4.5c; 4.5a offers **full direct manipulation** (drag column borders, resize pictures by handles, drag floating pictures, drag rows, select a range of cells with the pointer; every gesture has a keyboard or card equivalent, see goal 6); **a picture can be pasted from the system clipboard** (screenshots and copied images); the rest of the draft is approved as written; and the gestures are built on **an object map in the layout, an object selection in the session and handles drawn by the view** (approach A below).

## Intent

A thesis needs tables, figures and notes, and the owner's rule for Write is that nothing Word makes easy may be harder here. Today Write opens, lays out and edits the text of these elements, but cannot make one: there is no way to insert a table, a picture or a note, and the pointer knows only text. 4.5a adds the tools, the objects the pointer can act on, and the package support the new content needs (a picture is a new part in the file, a first note is a new notes part). The ground truth stays the same as in 4.3 and 4.4: what Write writes, Word opens without repair, and the incremental layout equals a full layout after every step.

## What exists today (checked 2026-11-24)

- **Tables:** `Table`, `TableRow` and `TableCell` are in the model with property bags, a grid (`GridColumns`, with a kept original grid) and position ints that are not edit-proof (4.1 decision). The layout reads and lays them out (`TableModel`, `GridSolver`, `TableLayouter`, `BorderResolver`) including merged cells and repeated header rows, and draws them as fills and rules: **no column border or cell rectangle is exposed to the pointer.** Text in cells is editable (4.3a), nested tables are not entered by Move.
- **Pictures:** a picture is raw `w:drawing` XML kept as `UnknownRunContent`; the layout reads it (`FloatSpec.FromDrawing`, inline and anchored) and draws an `ImageItem` that has **no link to its model object**. `ImageCache` has a budget and a per-picture pixel cap (4.3c). `DocxFile` can create header and footer parts but **never a media part**; the save guard knows created parts and relationships to them, not binary media.
- **Notes:** `Note`, `NoteCollection`, typed `FootnoteReference` and `EndnoteReference`, laid out at the page bottom (footnotes) and the end (endnotes); the text of an existing note is editable on the page. The layout's plan cache and filler state already key on note state. A document may have no notes part, and the settings part lists the separator notes.
- **Selection** is a `TextRange`; there is no object selection. **Pointer** handling is in `PageView.Editing.cs` (press, move, release, capture lost) and is text only.

## Goals

1. **Tables.** Insert (grid picker up to 10 columns by 8 rows, and a card for any size up to 63 columns, the layout's cap, and 500 rows); add and delete rows and columns before and after; merge a cell range and split a merged cell; select a row, a column and the whole table; set borders (none, all, outside, box, per side, colour, width, style; applied to the cell range) and cell shading from the fixed colour list; repeat a header row on each page; set the table's width and each column's width (a card, and by dragging a border); distribute columns evenly; delete the table. A new table is full text width with single 0.5 pt borders on every side and equal columns, with one empty paragraph in each cell, and the body always keeps a paragraph after it (the table-last rule of 4.4a) **(call)**.
2. **Pictures.** Insert from a file (PNG, JPEG, GIF, BMP and TIFF, whatever Skia decodes and Word reads) inline at the caret **(call: no SVG, EMF or WMF on insert)**; **alt text is asked for and stored** (`descr`; accessibility) **(call)**; select a picture; resize by corner and edge handles (aspect ratio kept by default, Shift frees it) and by a card (width, height, lock ratio, reset to the original size); change an inline picture into a floating one and back; floating picture wrap: square, top and bottom, in front of text, behind text (tight and through stay drawn as square, a known limit); **drag a floating picture** (its anchor moves to the paragraph under the pointer; position kept relative to the column and the anchor paragraph) and nudge it with the arrow keys; delete. A picture is one unit like a field: the caret steps over it, Delete removes it. **Paste a picture (owner):** Ctrl or Cmd with V (and the paste command) inserts an image from the system clipboard inline at the caret, replacing a selection as text does. Precedence on paste: Write's own fragment first, then an image, then text (a clipboard that holds both an image and text, as a spreadsheet cell range does, keeps pasting the text unless it holds no text: **call**). The bitmap is taken as PNG when the clipboard offers it and otherwise as the system bitmap format (DIB on Windows, TIFF on macOS) converted to PNG by Skia, never re-encoded lossily; its size is its pixel size at 96 DPI (screenshots) capped to the text width with the ratio kept; no card and no alt text is asked on a paste (the field is empty and `picture.properties` sets it), and a paste is one history step. The same limits as the insert apply (50 MiB, 32,000,000 pixels, header probed first, bytes untrusted) and a paste where a picture is refused (header, footer, note, comment, restricted content control) falls through to text or does nothing, with the reason shown. A copy of a picture inside Write goes through Write's own fragment so the picture keeps its identity and bytes (see the builder section); only an image from another program arrives as a bitmap.
3. **Footnotes and endnotes.** Insert a footnote or endnote reference at the caret; the caret moves into the new note at the page bottom (footnote) or the end (endnote) so the user types at once; Escape or the command "Back to the text" returns to the reference; double click on a reference goes to its note and a double click on the note number goes back; deleting the reference deletes the note (one history step, undone together); notes numbered by position (the layout already does this); a note's id is allocated, never reused while the reference exists. Footnotes and endnotes are refused where Word refuses them: headers and footers, other notes, comments, and in the writing view, which draws no note (reason shown) **(call)**.
4. **The package carries what is new.** A first footnote or endnote creates the notes part with its separator notes, the settings entries and the relationships Word expects; a picture's bytes are held by the model until the next save and written as a new media part with its content type and relationship, in the user's save, the recovery copy and the snapshot guard alike; nothing a user cannot see is left dangling (no relationship id without a part, no picture part without a use after the save, no `docPr` id used twice) **(call: an undone picture insert leaves no media part in the next save)**.
5. **Never break (acceptance).** After every command and gesture of this milestone and after undo and redo of each, the incremental layout equals a full layout exactly, the saved file read again gives the same model, Word opens the files without repair, and typing stays within its limit with the new panes and handles present (tests, the oracle of 4.3a to 4.4b, `word-open-check`).
6. **Every gesture has a non-pointer route.** The pointer makes the work fast, but no function is pointer-only: column widths and row height by the table card (reached by the ribbon, the context menu and the command search), picture size and wrap by the card, floating position by the arrow keys and the card, cell range by Shift and the arrows, a row move by the commands "Move row up" and "Move row down". The object selection is announced to assistive technology like a text selection (the selected object and its alt text or table position) **(call)**.

## Non-goals and anti-goals

- No table styles gallery, no converting text to a table or back, no sort, no formulas, no nested table creation (a table cannot be inserted into a cell; existing nested tables stay as they are) **(call)**, no table in a header, footer or note (Word allows it; deferred, the same as notes), no captions on a table or picture (4.5b), no picture cropping, rotation, effects, reflow around an irregular shape, text boxes or shapes (kept, never edited), no screenshot tool, no picture by drag and drop from the file manager and no copied image file pasted from the file manager (only image data on the clipboard; a backlog item), no linked pictures (external relationships are never fetched), no footnote options dialog (numbering format, restart each page or section, placement stay as the file has them), no conversion between footnote and endnote.
- Anti-goals: a handle or guide that reaches print or PDF; a gesture that changes the model before the release (a drag edits once, on release); a gesture that cannot be undone as one step; a table, picture or note the file does not carry exactly after a save; a note whose number on screen differs from Word's; a drag that leaves the pointer capture or the selection in a state the next click cannot recover from.

## Constraints that bind

- Everything of `CLAUDE.md`: Native AOT, English source with German localization ("Sie"), every command its own Lucide icon and a reason in every disabled state (`WriteCommandRules`), strings in both resx files (LF), cards through `CardFooter` and registered in `CardFooterTests.Entries` and `CloseGuardTests.CardsAreBuiltByCardFooter`, no warning suppressed, a key never uses Ctrl plus Alt (AltGr is text).
- **The model is the vocabulary:** a picture, a table and a note are written through typed accessors and views in `Raffica.Write.Model` (no second storage); anything Write does not understand stays as `UnknownContent`; new children are placed by `SchemaOrder`; the position ints of tables, rows and cells are re-derived by every table operation (a restructure replaces the table block as one `BlockChange`).
- **Every model change goes through the lease and `EditSession.Apply`, one history step per command or gesture, every raise attributed** (`DocumentEdits.Attribute`; the oracles `SnapshotCacheOracleTests` and `LayoutOracle`). A change that adds or removes notes, media or settings entries returns a result the session routes like the `Sections` and `Style` results (a new swap record with an undo that restores the previous state), never a second history. `EditHistory` clears itself after a change behind its back.
- **The object map is part of the layout, not of the pages' drawing:** immutable per `LaidOutPage`, built with the page, equal under incremental and full layout (the oracle compares it), read on the UI thread through `TryGetPage`; handles, guides and the drag outline are drawn by the view over the page and never enter a `LaidOutPage` or the print path. `Render` touches no visual. A new pointer state needs the capture-lost and Esc cases of the existing text drag.
- **Start cost.** Nothing of tables, pictures, notes, the new ribbon tabs' pickers, the grid picker or the object map is built before first use (`StartupCreatesNoObjectWork`); the Home band's width hint is unchanged (`RibbonStartupTests`) and `--measure-startup` is compared with the commit before 4.5a. A document without tables or pictures builds an empty object map cheaply.
- **Speed.** A command on the thesis has the limit that the first measurement sets (budget times 1.25, the method of 4.4a and 4.4b, a fixed limit on every platform, the 100 ms aim named and claimed only when met). A pointer move during a drag costs at most 16 ms of CPU at the 95th percentile (outline and hit test only, no layout), measured by a `--measure-gesture` run on the thesis. `typing`, `format`, `structure` and `sections` are not loosened.
- **Pictures:** at most 50 MiB of bytes and 32,000,000 decoded pixels per picture on insert (the cap of `ImageCache`; larger is refused with the reason); the bytes are untrusted (the header is probed before the decode, `ImageHeader`) and no picture's bytes, name or alt text is put into a log line or an exception message. Inserting a picture calls `ImageCache.Clear` and triggers a prefetch (the rule of 4.3c).
- **Notes:** the document's own `w:footnotePr` and `w:endnotePr` are honoured and never rewritten except to add the separator entries a new notes part needs.

## Approaches considered

1. **A. Object map in the layout, object selection in the session, handles drawn by the view (chosen, owner, 2026-11-24).** The layout publishes per page what is under the pointer (picture boxes with their model identity, table grids with column borders, row edges and cell rectangles); the session gets an object selection beside the text range; the view draws handles and the drag outline as a non-printing overlay; a drag edits once on release. Fits the rules of the code base (immutable pages, no visual touched in a render pass, one history step per operation, the layout oracle) and is testable with pure geometry.
2. **B. As A, but the model changes live during the drag.** Text reflows as the user drags. Rejected for 4.5a: every pointer move would be an edit through the lease and a layout pass, which has to hold the 16 ms limit and multiplies the states the oracle sees. It can be built later on top of A (the object map and the selection are the same).
3. **C. Handles as real controls in an overlay layer, like the section chips.** Accessible without drawing code, but a table grid is dozens of moving parts that must be repositioned after every layout change, and a border drag or a cell-range drag is awkward through controls. Rejected.

## How it is built (the parts, in order of dependence)

1. **Notes first (smallest, no gestures; proves the package support).** `NoteChange` swap and result; footnotes and endnotes parts, separators and settings entries created when absent; insert, jump and back, delete with the reference; the page bottom edit already exists; Word check rows.
2. **The object foundation.** `ObjectMap` per page (`PictureBox` with identity story, paragraph and run, `TableGrid` with column borders, row edges, cell rectangles and the table's block index); `HitObject(page, x, y)` on `DocumentLayout`; `ObjectSelection` in the session (a picture; a table, a row, a column or a cell range) with the selection events, the keyboard rules (Esc clears; Shift and arrows extend a cell range; Delete) and the handle geometry in pure code; the view's handle overlay and the capture-lost cases.
3. **Tables.** The editor operations (`TextEditor.Tables.*`), the cards and ribbon, the table gestures (border drag, row drag, range drag), the Tab rules in a table (Tab and Shift+Tab move between cells, Tab in the last cell adds a row; the order against the list rule of 4.4a is decided in the plan with a case table and a test for each).
4. **Pictures.** The media store in the model, `DocxFile` writing media parts (a new kind of created part in the save guard, in `DocxFile.SaveSnapshotAsync` and the recovery copy), the drawing builder (inline and anchored; `docPr` ids unique), the editor operations, the cards, the handle gestures, the floating drag and nudge, `PackageImageSource` reading pending media before the package, and the paste of a clipboard image (the image format on `IEditClipboard` on the three systems, the paste precedence, the bitmap to PNG step).

A plan that orders the work as these four stages lets each end green with its own oracle step kinds. The milestone stays one (call); if a stage grows beyond the plan, the roadmap split follows the 4.3 and 4.4 pattern.

## Ribbon and commands (call)

A new **Insert** tab (key tip `I`; Table, Picture and Notes groups) and a **Table** tab (key tip `T`; rows and columns, merge, borders, header row, widths) are added, each with the commands disabled with a reason outside their object. The Home band keeps its width hint. New commands (each with its own Lucide icon, strings in both languages and a `WriteMacMenu` line): `table.insert`, `table.rowAbove`, `table.rowBelow`, `table.colLeft`, `table.colRight`, `table.deleteRows`, `table.deleteColumns`, `table.delete`, `table.merge`, `table.split`, `table.borders`, `table.shading`, `table.headerRow`, `table.properties`, `table.distributeColumns`, `table.rowUp`, `table.rowDown`, `picture.insert`, `picture.properties`, `picture.wrap`, `picture.reset`, `picture.delete`, `note.footnote`, `note.endnote`, `note.back`. `WriteCommandCatalog.Find` skips them where the page view owns the key. There are no Ctrl plus Alt keys (Word's Ctrl+Alt+F and Ctrl+Alt+D cannot exist), so notes have no key; the command search (Alt+Q) and the ribbon are the routes.

## Word compatibility (what a file must satisfy)

A table needs a paragraph after it at the end of the body and at least one block in every cell, a `w:tblGrid` equal to the cells' widths, `w:gridSpan` and `w:vMerge` that agree with the grid; a picture needs a unique `wp:docPr` id, a valid `a:blip` embed, `w:drawing` placement and a content type for its extension; a notes part needs the separator and continuation separator entries and the settings references; every created part needs its relationship and content type; **a content control of the text, combo box, drop-down or date kind keeps one paragraph** (4.3a rule) and a table or note command refuses inside one. Checked on the Windows PC with `tools/word-open-check.ps1` and a new row set in `Docs/write-word-check.md`; a `WordCheckObjectFilesTests` writes the files through the editor into `RAFFICA_WORD_CHECK_DIR` as the section tests do.

## Known limits that will be named in the decision

Tight and through wrapping stay drawn as square; no EMF or WMF on insert or paste; no drag and drop of an image file and no image file pasted from the file manager; footnotes are not available in the writing view; no table or note inside a header or footer; nested tables cannot be created; a cell range that spans a nested table is refused; undoing a first note or picture leaves the created parts in the package until the next save drops the unused media (notes parts stay, as numbering definitions do).

## Rules settled after the review of this document (all calls)

A reviewer who had only this document asked nine questions; each is answered here so the plan does not guess.

1. **Where an object may be inserted.** A table: the body and the body of a content control that allows several paragraphs, never in a cell (no nested creation), a header, a footer, a note or a comment. A picture: the body and table cells (inline or floating-turned-inline in a cell), never in a header, footer, note or comment (the reason is shown; their media relationships are per part and deferred). A note reference: the body and table cells only. Content controls of the text, combo box, drop-down and date kinds refuse all three. Because a picture then lives only in the main part, the media store is document level and the relationship is the main part's.
2. **What counts as a picture.** The object map exposes a `w:drawing` whose graphic is a plain `pic:pic` (inline or anchored). Shapes, groups, text boxes, charts and SmartArt stay marked placeholders and are never selectable as pictures. A cropped picture (`a:srcRect`) is selectable and resizable: the extent changes (`wp:extent` and `a:ext`), the crop and every other child are kept. A rotated picture (`a:xfrm` with `rot`) is selectable, movable and deletable but not resizable (the reason is shown). Resize writes both extents and nothing else; the oracle and the Word check cover a cropped corpus picture.
3. **Anchor defaults and the drag.** An inline picture made floating gets Word's own defaults: `wp:anchor` with `positionH` relative to the column at its current offset, `positionV` relative to the paragraph, `distT` and `distB` 0, `distL` and `distR` 114300 EMU, `wrapSquare` on both sides, `behindDoc` 0 for "in front of text" (1 for "behind text"), `allowOverlap` 1, `layoutInCell` 1, `simplePos` 0, `relativeHeight` above every other drawing of the document. A drop on a paragraph in a table cell, a note, a header or a footer is refused (no-drop cursor, the floats there are inline boxes in the layout); a drop in another section or column anchors to the paragraph under the pointer with the offsets recomputed against it. The arrow-key nudge moves the picture 1 pt (with Shift, 10 pt); a nudge or a drag is one history step (a run of nudges coalesces per second). The layout must read back exactly what the editor writes (`FloatSpec` round trip test).
4. **Table structure rules.** Merge joins the cells of the range: the content of the merged cells is concatenated in order as paragraphs, empty paragraphs skipped (as Word), and nothing is lost. Split offers a merged cell back as its original cells (the content stays in the first cell); splitting an unmerged cell into several columns is not offered in 4.5a (reason shown). Delete row: a cell that continues a vertical merge is removed and the span above shrinks; a deleted row that holds the start of a vertical merge passes the start to the next row's cell. Delete column: a cell that spans the column shrinks by one, a cell that spans only that column is deleted with its content. Insert row or column inside a merged region extends the region (continuation cells, grid spans). No confirmation is asked (undo is one step). Every table command acts on the table that holds the caret or the object selection, and a caret in a nested table refuses with a reason (only top-level tables are edited by commands and gestures in 4.5a).
5. **Widths and layout mode.** A border drag moves the border between two columns (the two neighbours change, the table width is unchanged); dragging the right edge of the table changes the last column and the table width. The first write by a user to a table converts an autofit or percentage table to fixed layout (`w:tblLayout fixed`, `w:tblW` in twips, every `w:tcW` in twips, the grid equal to the cells), as Word does; reading never converts. The editor writes exactly what `GridSolver` reads back (a round trip test per table kind in the corpus).
6. **Styles.** A command that needs a style the document lacks adds it in the same step as a companion (as the heading switch of 4.4a did): the table style `TableGrid` (single 0.5 pt borders), the character styles `FootnoteReference` and `EndnoteReference` (superscript), and `EndnoteText` next to the existing `FootnoteText`. The step is a style change and goes through `Restyle` rather than `ApplyEdit`. The blank document's 24-style set does not change (its bytes stay deterministic); the styles are created on first use.
7. **Documents that refuse.** A prefix document (`IsPrefix`) refuses every command of this milestone, as the section commands do. An untitled tab, a restored recovery copy and a document opened from a file all accept them.
8. **Alt text flow.** The insert card has an optional "Alt text" field; Cancel aborts the whole insert, an empty field is allowed and stores no description, and `picture.properties` edits the text afterwards (one history step). There is no "decorative" flag in 4.5a.
9. **During a save.** Every command, gesture and key of this milestone is queued and replayed by the save queue of 4.3a, as the structure drops of 4.4a were; a drop queued during a save gives no feedback, which is accepted as in 4.4a. A pointer press that would start a gesture during a save only selects.
