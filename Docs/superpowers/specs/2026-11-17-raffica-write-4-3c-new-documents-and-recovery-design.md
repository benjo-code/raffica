# Raffica Write 4.3c: new documents and recovery (design)

Status: draft for approval, 2026-11-17. Milestone 4.3.3 of `Docs/roadmap.json`. The subproject spec is `Docs/superpowers/specs/2026-11-13-raffica-write-design.md` (sections 6 "Opening and saving" and "New documents", the autosave call); this document only settles how 4.3c builds what that spec already decided.

## Intent

After 4.3a (editing engine) and 4.3b (formatting) Write can edit and save a file that already exists. Two things still stop it from being a place to write: there is no way to start a document, and a crash or a power loss takes the unsaved text with it. 4.3c adds both. A user can choose "New document" and type into a document that carries Write's own style set, and whatever they typed is back after the process was killed, with at most about 30 seconds of typing lost. The third task is a debt of 4.2: the picture cache has no limit and decodes on the render thread.

## Goals

1. **New document.** A command and a key (Ctrl+N, ⌘N on macOS) open an untitled tab holding a blank document with the built-in style set of the spec: Normal, Heading 1 to 9, Title, Caption, TOC 1 to 9, Footnote Text, List Paragraph, Hyperlink, plus one multi-level numbering definition for headings and the bullet and number lists. Body Carlito 11 pt, headings Caladea, A4 with 2.5 cm margins, US Letter with 1 inch margins when the system region is the United States or Canada (the region read once through `RegionInfo`, tests pass it in).
2. **Untitled documents.** A tab may have no path. Its title is "Untitled", "Untitled 2" and so on (localized, English and German). Save on such a tab is Save as; the close question works as for any dirty tab; an untitled tab is not in the recent list until it is saved.
3. **Recovery copy.** While a tab has unsaved changes Write writes a recovery copy every 30 s and when the window loses focus. After a crash the next start offers the copies (Restore, Discard). Writing the user's file happens only on Save.
4. **Autosave setting.** The shell's stored autosave value (`ShellSettings.Autosave`, on by default) is shown in Write's settings dialog and switches the writing of recovery copies. Off means no copies are written; copies that already exist are still offered at the next start. The shell's label "Autosave" / "Automatisch speichern" would say that the user's file is saved by itself, which Write never does, so Write shows the row with its own label (call, see "Calls settled after the builder check").
5. **Picture cache.** `ImageCache` gets a byte budget with least-recently-used eviction and a pixel cap, and the app never decodes a picture on Avalonia's render thread.

## Non-goals and anti-goals

- No edit journal, no incremental or partial recovery file: a copy is always a complete DOCX.
- No templates, no "New from template", no style gallery or style designer (the spec says templates come later).
- No shared crash guard for Write. The 4.3a decision named it as a follow-up of 4.3c, the roadmap task list of 4.3.3 never did, and the owner decided on 2026-11-17 to leave it out: it moves to 4.9 together with the update flow, the default-app services and the print services (the roadmap's "Scope changes" records this).
- A recovery copy never replaces, touches or is merged into the user's file, and a failed copy never shows a card, never blocks typing and never makes the document dirty.
- Not in scope: recovery of the PDF app, the 4.8 hardening of hostile files (a recovery copy is a file Write wrote itself, but it is still opened through the normal untrusted-file path), the open owner gates of 4.2, 4.3a and 4.3b (they stay open and are not claimed here).

## Constraints that bind

- Everything of `CLAUDE.md` applies: .NET 10 Native AOT, no reflection-only code, English source with German localization in the "Sie" form, every command with its own Lucide icon and a reason in each disabled state, every card through `CardFooter`, new strings in both resx files.
- **Start cost.** Nothing of the blank document, the recovery store or the timer exists before it is needed (a test like `StartupCreatesNoEditorWork`, `StartupCreatesNoPickerWork`): the timer starts at the first edit, the recovery folder is read only after the first window is shown and the first sharp page is out, and the style set is built only when "New document" runs. The ribbon and the command search already read their catalog at start; a new command must not change the Home band's width hint (`RibbonStartupTests`).
- **Typing stays at most 16 ms.** A snapshot takes the edit lease on a pool thread only for the model read, as `WriteSaveFlow` does (`DocxFile.BeforeModelRead` and `AfterModelRead`); the UI thread never holds it across the write, and a request for the lease from the UI thread (an IME preedit) waits for that read only. Typing during a snapshot is not queued the way it is during a save (a snapshot is not a save scope); it simply stays out because the lease is held for the read. The `typing` measurement is re-run with the recovery timer active.
- **The model rules of 4.3a hold.** A snapshot reads a model that is consistent: it is skipped while the session is faulted, while a save runs, and when the revision equals the last one written. It never calls `MarkSaved`.
- **Files.** A recovery copy is written with `AtomicFile` (write next to the target, check, replace) and the `DocxFile` save guard; the folder lies under `AppFiles.ConfigDirectoryFor(settingsFile)`, so `--settings-file` redirects it and tests and measurements never touch the user's folder. No document text goes into a file name, a log line, an exception message or the sidecar's error text (`CLAUDE.md`: a file's text is never printed).
- **Roadmap and docs.** The roadmap entry of 4.3.3 gets its plan link and statuses, the "Scope changes" section records the crash guard move, `Docs/DECISIONS.md` gets one entry "Raffica Write: new documents and recovery (M4.3c)", `CLAUDE.md` gets a "Write recovery (M4.3c)" section in the style of the previous ones, and `CHANGELOG.md` `[Unreleased]` names the user-visible changes.

## Approaches considered

**A. Full DOCX snapshot through the existing guarded writer (chosen, the builder's call confirmed by the owner's "your pick").** A recovery copy is `<id>.docx` plus `<id>.json` (title, original path if any, time, Write version, the revision's wall time) in the `recovery` folder, one pair per open document, written on a pool thread under the edit lease for the model read only. Restoring opens the DOCX through the ordinary open path. Cost: a snapshot re-serializes every loaded model part and writes a zip, which on the thesis is the same work as a save; it is skipped when nothing changed and runs at most once at a time. Benefit: one file format, the existing guard and atomic replace, and every later milestone (4.4 to 4.6) is recovered for free because a snapshot is whatever the model saves.

**B. An edit journal replayed after the crash.** Each write would be tiny, but every kind of edit needs a record and a replay, 4.4 to 4.6 would each have to extend it, and a replay has to equal the live model, which is the risk the "incremental equals full" rule guards against. Rejected.

**C. Snapshot plus journal.** Carries both costs without removing either. Rejected.

## Design

### Blank document

A new type in `Raffica.Write.Docx` (not the model: the model references nothing) builds the bytes of a minimal, valid package: `[Content_Types].xml`, `_rels/.rels`, `word/document.xml` (one empty paragraph and the final section: page size and margins from the region), `word/styles.xml` (the style set and the document defaults), `word/numbering.xml` (the one multi-level definition and the list definitions), `word/settings.xml`, `word/fontTable.xml` and the core properties. The bytes are opened with `DocxFile.Open(bytes)`, so the tab holds a normal `DocxFile` with no origin, and the 4.1 round trip, the save guard and the layout need no special case. The style set is data in code with a unit test per style (it resolves through `StyleResolver`, the numbering indents show with `document.Numbering` as the third argument, the heading chain is outline levels 0 to 8). A test saves a blank document, reopens it, compares the model and checks that Open XML SDK validation reports no schema error. The look of the style set (sizes, spacing, colours of headings, the Caption and Hyperlink looks) is one design pass with the shell's design direction (`PRODUCT.md`, `Docs/design/direction-d`); the result is recorded in the DECISIONS entry. The owner looks at it in Word (gate below).

### Untitled tabs

`WriteTab` takes a nullable path: `Path` is `null` and `Title` is the localized "Untitled N" for a new document; the number is the smallest free one in the window. `Rebind` after Save as gives it the path. Every consumer of `WriteTab.Path` (title bar, recent, `WriteWorkspace.Find`, `OpenTargetGuard`-like checks, `WriteSaveFlow.SaveOverOriginalAsync`, the window title, hand-over) is read once and made null-safe. `SaveCommandState` makes Save on a pathless tab behave as Save as (the command is enabled when the tab is dirty or untitled, the reason texts follow). An untitled tab that was never edited closes without a question; once edited it asks. The tab is not added to the recent list.

### Recovery store

`Raffica.Write/Recovery` (UI-free where possible, in the app project unless the builder finds it shared): `RecoveryStore` (folder, entry id = a GUID per tab, write, read the list, delete, all through `AtomicFile`), `RecoveryEntry` (id, title, original path or null, time written, document size), `AutosaveScheduler` (the 30 s timer per window that starts at the first edit, the deactivation trigger, the "revision already written" rule, one snapshot at a time, a bounded retry after a failure, no card), and `RecoveryFlow` (the start offer and its two outcomes). The scheduler is created by the window on the first edit and never at start. A snapshot uses a variant of `DocxFile.SaveAsync` that writes a copy and changes neither the origin, the stamp nor the snapshot of the file (the 4.1 rule "a save to another path changes neither", so the existing `SaveAsAsync` overload for another path is the base); the builder confirms that it needs no new save entry point.

A copy is deleted when its tab is clean again (after a Save or a Save as that marked the revision saved), when its tab is closed after Save or Don't save, and when the user discards it. A clean exit therefore leaves the folder empty; anything left in it at the next start is what a crash left. A copy of a document the user closed with "Don't save" is deleted, never offered.

### Offer and restore

At the next start, after the first sharp page of the first window (or at once when the window has no document), and only in the instance that owns the single-instance lock (a second instance hands over and does not look), `RecoveryFlow` reads the folder. With one or more entries it shows one card (`CardFooter`: Restore as the primary, Discard, no Cancel-that-keeps: closing the card by Esc leaves the copies for the next start): the list shows each entry's title and the time of the last copy, never text from the document. Restore opens each entry as a dirty tab through the ordinary open path (`DocumentOpener` on the copy's bytes), titled with the original name or "Untitled N", with the copy's sidecar path remembered only as the suggested name and folder of Save as. A restored tab is never bound to its old path silently: Save on it is Save as, the picker confirms an overwrite, and the existing "changed on disk" rules need no special case. The copy is deleted after the restored tab has been saved or closed, not at restore, so a second crash does not lose it. An unreadable or hostile copy (the open fails) is reported with the normal open error wording and offered for deletion; it is never deleted silently.

### Autosave setting

`WriteSettingsController` passes `ShowAutosave: true` and an `AutosaveLabel` (a new optional member of `SettingsDialogOptions`; null keeps the shell's text, so the PDF app and the gallery are unchanged). Changing it applies at once to every running scheduler (stop the timer, delete nothing). The label is Write's own string in both languages (see below).

### The picture cache

`ImageCache` keeps its synchronous `Get` for the bench, the tests and the first sharp page, and gains: a byte budget on decoded pixels (width times height times four) with least-recently-used eviction, a pixel cap per picture read from the header probe (`ImageProbe`, already read once per picture at layout; a picture above the cap is not decoded and is drawn as the marked box with the same wording as a metafile), `TryGet` (the decoded image or null, never decodes) and `Prefetch` (asks for a decode on a pool thread and raises an event when it is ready). The app's page view prefetches the pictures of the pages in view and one page each side when the visible range changes, draws a marked box for a picture that is not decoded yet and invalidates when the decode arrives; the render thread calls `TryGet` only. Eviction never disposes an image a draw is using: it happens under the existing `DrawGate` or hands out a reference-counted image (the builder chooses; the gate order of 4.3a, "the gate is closed before the cache is disposed", stays). Proposed starting values, to be set by measuring the thesis and the corpus pictures and recorded in the DECISIONS entry: budget 256 MiB of decoded pixels, cap 32 million pixels per picture (128 MiB decoded). The cap is always at most half the budget, so one picture can never exceed the budget and two of the largest allowed fit together; a test pins that relation. These numbers are the designer's call, not the owner's. Write has no memory limit in `s_writeBudgets` yet; the memory of a picture-heavy file is recorded, not judged.

### Tests

- Blank document: each style resolves; the Letter and A4 choice by region; numbering indents; save, reopen and compare; SDK schema validation of the saved bytes; a corpus-style check that Write's layout lays the blank document out as one empty page (`LayoutOracle`).
- Untitled tabs: title numbering, Save as on the first Save, the close question, no recent entry, every null-path consumer.
- Recovery store and scheduler with a fake clock: nothing before the first edit, the 30 s and the deactivation trigger, the "revision already written" skip, the faulted and saving skips, one at a time, a failed write is silent and retried, the setting off writes nothing, deletion on clean, on close and on discard, the folder follows `--settings-file`.
- Offer and restore: one card for several entries, Esc keeps them, Restore opens dirty tabs titled as before, Save on a restored tab is Save as, the copy is deleted only after save or close, a corrupt copy is reported and kept until the user decides.
- **The acceptance test (killed process).** A small console harness in the Write app test project runs the real `RecoveryStore`, `AutosaveScheduler` and `DocxFile` in a child process with a short interval: it makes a document, types known text through the editor, signals "copy written" on a pipe and is then killed with `Process.Kill`; the test process then runs the restore code on the same folder and compares the text paragraph by paragraph with what was typed. A second case kills it between two copies and asserts that the older copy is whole (no half-written file). Native AOT is not required for this test; the owner gate below covers the real app.
- Picture cache: the budget evicts the least recently used, `TryGet` never decodes, a picture above the cap is a marked box, `Prefetch` raises its event once, eviction while a draw runs is safe (the existing `DrawGate` tests extended), the pixel output of a picture page is unchanged (oracle).
- Measurements: `typing` and `format` re-run with the scheduler active and the new `typing-snapshot` case (budget 16.0 ms unchanged), the start (`cold`, `warm`) against the previous release, the time of one snapshot of the thesis recorded (not judged), memory with a picture-heavy file.

## Calls settled after the builder check

A fresh reader of this document asked eight questions; none needs the owner. The answers, as calls of the designer (the owner can change any of them):

1. **Label of the setting.** Write shows the stored `ShellSettings.Autosave` value under its own label: English "Keep a recovery copy of unsaved work", German "Wiederherstellungskopie ungespeicherter Arbeit anlegen". Write never saves the user's file by itself, and the shell's wording would say so. The value and its file stay the shell's (one switch for the app, as the spec says).
2. **Restore does not bind to the old path (deliberate).** A recovered text should never overwrite the file it came from without the user choosing to, and a restored tab has no origin stamp to check against (the file may have changed since the crash). Save on a restored tab is Save as with the old name and folder suggested; the picker's overwrite confirmation is the user's "yes, replace it". This costs one extra click and removes a class of silent overwrites.
3. **Windows and tabs.** The store is one per process. One scheduler per window covers that window's tabs (a tab never moves between windows). The offer is made once per process, by the first window that is shown (on macOS, the first window made after a start with none); a window made before the offer ends waits for it, never asks again. A closing window deletes a tab's copy only after Save, Don't save, or when the tab is clean.
4. **Whose copies are offered.** The sidecar holds the writer's process id and its start time. An entry whose process is alive and is not the reader is a live instance's copy and is skipped (never offered, never deleted); an entry whose process is gone, or whose id is reused by a process with a different start time, is a crash's leftover. The single-instance rule stays as the first line (a second instance hands over and does not look); this check is the second line for a failed hand-over. A run with its own `--settings-file` has its own folder, so it never meets another run's copies.
5. **Typing during a snapshot.** The lease is held only for the model read (the 4.3a decision: a few milliseconds), and a keystroke that arrives meanwhile waits for it. This is measured, not assumed: a new case `typing-snapshot` in the app measurement (switch and `measure.cs` case, the editor bench gets the same) types while snapshots run back to back and is judged like `typing` (worst p95, 16.0 ms, CPU cost including the wait for the lease); the lease-held time of a snapshot of the thesis is recorded. If it does not pass, the read is bounded further (serialize the changed parts only, or read in slices), and the milestone does not close with a limit loosened.
6. **Pictures on page 1.** The open pipeline decodes the pictures of page 1 on the pool thread before the first sharp page is shown, so the first draw finds them (picture-heavy first pages may open a little later; measured with the corpus and recorded, and the budget `first page ≤ 100 ms` of the engine is unchanged because that bench has no pictures to wait for in the thesis). Pictures of later pages are prefetched when the visible range changes; if a fast scroll outruns the prefetch, the page shows the marked box and is invalidated when the decode arrives. The render thread never decodes. The pixel oracle forces a synchronous decode through the library's `Get`, so "pixel output unchanged" compares pictures with pictures; the app path has its own tests for the box and the invalidation.
7. **Budget and cap.** Settled in "The picture cache": the cap is at most half the budget.
8. **Headings in the blank document.** Heading 1 to 9 are linked to outline levels 0 to 8 and carry no `numPr`: a new document shows "Introduction", not "1 Introduction". The one multi-level definition exists so that the bullet and number list styles use it and so that 4.4's heading numbering command has a definition to switch on. Numbered headings are 4.4's, not 4.3c's.

## Owner gates (stay open, not claimed by the milestone)

Word opens a blank document made by Write and a recovery copy restored and saved without a repair prompt and shows the style set as designed; the real app on Windows, the Linux laptop and the Intel Mac is killed during typing and the next start offers the text; the autosave check box on a real display; the `typing` and start measurements on the Linux laptop and the Intel Mac. The gates of 4.2, 4.3a and 4.3b are unchanged.

## What is left to the builder

The names of the new types and folders as long as the rules above hold; whether the recovery store lives in the app project or in `Raffica.Hosting`; the exact sidecar fields; the retry count after a failed copy; the eviction mechanism (gate or reference counting); the final values of the byte budget and the pixel cap after measuring; the order of the tasks; the wording of every new German and English string (the "Sie" form); the Lucide icon for "New document".
